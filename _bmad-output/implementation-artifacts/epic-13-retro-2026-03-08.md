### 业务成果

Epic 13 为 Rnix 构建了完整的交互式智能体调试系统，实现类 GDB 的调试体验：

**调试会话管理：**
- `rnix gdb <pid>` 附着到运行中的智能体
- 双通道事件流（DebugChan + LogChan）
- 独立连接 detach 机制（不阻塞事件流）

**断点系统：**
- 四种断点类型覆盖智能体执行的关键节点
- syscall 断点：精确匹配特定系统调用
- reasoning 断点：每次 LLM 调用前暂停
- quality 断点：输出内容模式匹配或规则评估
- budget 断点：token 消耗阈值触发（软限制，区别于硬限制 budget_exceeded）

**单步执行：**
- step syscall：逐个 syscall 单步
- step reasoning：逐个推理步骤单步
- 一次性 step mode 自动清除，与持久断点共存

**状态检查与热修改：**
- inspect context：查看上下文分段信息和 token 估算
- set model：运行时切换 LLM 模型
- set context append：追加上下文内容
- set skills add：记录技能到能力列表
- set env：设置环境变量

## 成功与优势

1. **渐进式架构扩展模式** — 4 个 story 严格遵循渐进式构建策略：13-1 建立 IPC 基础 → 13-2 添加断点机制 → 13-3 复用断点暂停实现单步 → 13-4 继续扩展 set 命令。每个 story 自然复用前一个的基础设施，零架构返工。

2. **独立机制设计（关注点分离）** — gdb 暂停机制（gdbPauseCh）与 Signal 系统的 SIGSTOP/SIGCONT（resumeCh）完全解耦。两套系统互不干扰，避免了调试操作影响进程正常信号处理。这是优秀的工程判断。

3. **IPC 独立连接模式** — Story 13-1 建立的 `SendDetach` 独立连接模式在后续 story 中被 `SendGdbCommand` 完美复用。命令传输与事件流解耦，避免了双向通信的复杂性。

4. **Code Review 持续高价值** — 4 个 story 共发现 11 个 HIGH 级别问题，全部为功能缺陷（协议声明未实现、AC 违反、必要提示符缺失等），每一个都在进入下个 story 前被修复。Code Review 防止了 11 个功能性 bug 进入后续 story。

5. **Dev Notes spike 模式第四个 Epic 连续验证** — 从 Epic 10 延续至今，每个 Story 的 Dev Notes 包含详尽的技术参考（源文件路径、行号、接口签名、时序图），直接支撑了开发质量和 Code Review 效率。

6. **零回归** — 全 epic 期间 19 个测试包始终通过（-race 检测），历史功能无一退化。

## 挑战与成长领域

1. **AI 生成代码的"声明-实现"一致性缺陷** — 11 个 HIGH 问题中，大部分是"Story/Task 声明了功能但代码未实现"模式。例如：
   - 13-1：声明了 `gdb_prompt` 事件类型但未定义常量
   - 13-1：声明了"单 attach 防冲突"但未检查
   - 13-1：声明了 `gdb>` 提示符但未显示
   - 13-3：声明了 step 暂停时传递 syscall_name/step_number 但未实现
   - 13-4：声明了测试但测试不存在

   **模式总结：AI 倾向于在设计文档中描述完整功能，但代码实现时遗漏部分细节。Code Review 是唯一的防线。**

2. **并发测试中的死锁模式** — 13-2 开发中多次遇到 GdbPause 测试死锁：GdbPause 阻塞调用 goroutine，测试必须在后台 goroutine 中运行暂停操作。这是 channel close 暂停范式的固有挑战，每次遇到都需要调试理解。

3. **IPC 协议细节不一致** — 多个 story 出现 server 端返回的 key 名（如 `"id"` vs `"bp_id"`）与测试期望不匹配的问题。这表明 IPC 协议的契约定义不够严格，依赖隐式约定。

4. **MVP 范围边界管理** — Story 13-4 中 `set skills add` 和 `set env` 最终只实现了存储功能，未真正注入到运行时。虽然 Dev Notes 明确了这一决策，但产品层面这些功能的实用性有限。需要在后续 story 中补齐或明确标记为技术债。

## 关键洞察

1. **渐进式 story 分解是 gdb 类复杂系统的正确策略** — 4 个 story 从 attach 到断点到 step 到 set，每个建立在前一个之上，复杂度可控。如果将 4 个 story 合并为 1 个 story，复杂度将急剧上升。

2. **"声明-实现"一致性检查应纳入 Code Review 标准清单** — 11 个 HIGH 问题中至少 8 个可以通过系统性地逐项比对 Task 描述与代码实现来发现。这应成为 Code Review 的标准步骤。

3. **独立连接模式是 IPC 双向交互的最佳实践** — 事件流（长连接、服务端推送）与命令传输（短连接、请求-响应）使用不同的连接，避免了多路复用的复杂性。这个模式值得在 Epic 14 中继续沿用。

4. **Channel close 暂停范式的测试模式应标准化** — 所有使用 `chan struct{}` + close 的暂停测试都需要后台 goroutine，这应该作为项目级的测试模式记录在开发文档中。
