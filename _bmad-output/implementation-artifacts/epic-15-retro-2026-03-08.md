### 业务成果

Epic 15 为 Rnix 构建了完整的分布式追踪和上下文分析系统，实现两大能力域、五层功能：

**分布式追踪域（Story 15.1 ~ 15.3）：**
- Compose 编排自动生成 TraceID，IPC 消息自动携带 TraceID/SpanID
- SpanRecorder 在 Kernel 中记录 Span 数据（syscall 计数、token 消耗、起止时间）
- JSONL 持久化到 `.rnix/traces/<trace-id>/spans.jsonl`
- `rnix trace <trace-id>` 树状视图展示所有 Span 的时序关系和依赖链
- `rnix trace blame <trace-id>` 自动分析关键路径、耗时/Token Hotspot、错误传播链

**上下文分析域（Story 15.4 ~ 15.5）：**
- `rnix ctx-profile <pid>` 将上下文分为活跃/温/冷/泄漏四类，识别大消费者并给出优化建议
- `rnix ctx-growth <pid>` 基于 token 历史预测增长趋势，设置 warning/critical 两级告警
- Budget warning 集成到 reasonStep，通过 LogChan 和 SyscallEvent 传递告警
- Token 历史使用环形缓冲区（50 条容量），O(1) 写入开销

## 成功与优势

1. **双域五层渐进式架构执行完美** — 15-1（TraceID/Span 基础设施）→ 15-2（追踪视图）→ 15-3（blame 分析）构成追踪域的三层递进；15-4（上下文分类）→ 15-5（增长预测）构成分析域的两层递进。两个域虽然面向不同的用户场景（跨进程追踪 vs 单进程上下文分析），但共享了一致的工程模式（debug 包分析逻辑 + IPC 协议扩展 + CLI 命令注册）。五个 story 之间零架构返工。

2. **"本地操作 vs daemon 操作"设计决策前置彻底执行** — 这是 Epic 14 回顾行动项 #3 的直接成果。15-1 的 Dev Notes 明确指出"Span 记录是 daemon 端操作，Span 查询是本地文件操作"。15-2 和 15-3 均为纯本地文件操作（不需要 daemon），15-4 和 15-5 是 daemon 操作（通过独立 IPC 方法）。这个前置决策使得每个 story 的测试策略非常清晰：本地操作用文件系统 fixture 测试，daemon 操作用 IPC mock 测试。

3. **IPC 扩展模式成熟且高效** — Epic 15 新增了 2 个 IPC 方法（ctx_profile、ctx_growth）和 4 组协议字段扩展，所有扩展都遵循了已有的非流式请求/响应模式。从 Epic 13 的 gdb_command（复杂流式协议），到 Epic 14 的 record_start/stop/fork_continue，再到 Epic 15 的 ctx_profile/ctx_growth，IPC 协议扩展已经形成了可预测的标准化流程。

4. **JSONL + metadata 持久化模式第三次验证** — Epic 14 确立的 JSONL 模式在 15-1 的 SpanWriter/SpanReader 中被完美复用。Span 持久化路径（`.rnix/traces/<trace-id>/spans.jsonl`）与 Recording 持久化路径（`.rnix/records/<record-id>/`）平行但独立，验证了这一模式的通用性。

5. **ctx-profile 独立 IPC 方法的正确决策** — 15-4 选择了独立的 `MethodCtxProfile` 而非通过 gdb_command 实现，避免了 gdb attach 的独占锁问题。这使得 ctx-profile 可以在不中断运行中智能体的情况下分析其上下文，是一个关键的架构决策。

6. **组合矩阵和"不要做"清单持续发挥价值** — 所有 5 个 story 均包含详细的组合矩阵和 8-10 项"不要做"约束，有效防止了范围蔓延。特别是 15-1 的组合矩阵涵盖了 11 个交互点（Compose Engine、IPC Send/Recv、emitEvent、reasonStep、reapProcess、非 Compose 场景、Record 系统、strace、fork-continue、gdb、Kill/Signal），确保了 TraceID 传播与现有系统的兼容性。

7. **环形缓冲区模式的引入** — 15-5 在 Process 中引入的 tokenHistory 环形缓冲区（50 条容量）参考了已有的 logHistory 模式，实现了 O(1) 写入和有限内存占用。这是对"不阻塞 reasonStep"约束的直接响应。

## 挑战与成长领域

1. **两域之间的连接较松散** — 追踪域（15-1~15-3）和分析域（15-4~15-5）虽然共属 Epic 15，但功能上相对独立。Trace blame 分析的是跨进程的 Span 数据，而 ctx-profile/ctx-growth 分析的是单进程的 Context 数据。两者没有直接的数据流连接（trace blame 无法引用 ctx-profile 的分类结果）。这不是一个缺陷，但说明 Epic 15 实际上包含了两个半独立的特性集，分解为两个更小的 Epic 可能更精准。

2. **maxSteps 在 handleCtxGrowth 中硬编码为 50** — 15-5 的 Completion Notes 明确记录了这一限制：ProcInfo 缺少 MaxSteps 字段，因此 handleCtxGrowth 使用了硬编码的 50。这意味着如果用户配置了不同的 maxSteps，增长预测的 PredictExhaust 判断可能不准确。

3. **Budget Warning 集成测试被推迟** — 15-5 的 Completion Notes 记录"Budget warning integration tests (ATDD Tests 16-17) deferred: require full LLM driver mock"。这意味着 budget warning 通过 emitLog/emitEvent 传递的完整路径没有端到端验证，只有单元级别的测试。

4. **上下文分类使用固定窗口（Active=4, Warm=6）** — 15-4 的分类启发式是 MVP 级别的：最后 4 条消息为 Active，接下来 6 条为 Warm，更早的为 Cold。这对于不同推理模式的智能体可能不够准确（例如频繁工具调用的智能体每步可能产生 3-4 条消息）。Dev Notes 已标注"后续可演进为更精细的引用分析"。

5. **CLI 测试薄弱问题延续** — 与 Epic 14 技术债 #10 一致，Epic 15 的 CLI 测试（trace_test.go、ctx_profile_test.go、ctx_growth_test.go）主要验证命令注册和基本参数解析，缺少完整的 E2E 测试（创建真实 trace 数据 → 运行 CLI → 验证输出）。debug 包的单元测试覆盖了核心逻辑，但 CLI 集成层的测试覆盖依然薄弱。

## 关键洞察

1. **"分析逻辑在 debug 包、CLI 在 cmd/rnix、IPC 在 ipc 包"三层分离模式已稳定** — 从 Epic 13 的 gdb 命令，到 Epic 14 的 record/replay，再到 Epic 15 的 trace/blame/ctx-profile/ctx-growth，这个三层模式被反复验证。分析逻辑（AnalyzeTrace、AnalyzeContext、PredictGrowth）可以独立单元测试，IPC 层只负责数据传递，CLI 层只负责格式化输出。这是项目的核心架构模式。

2. **IPC 扩展的"两步走"模式成熟** — 新增功能如果需要 daemon 数据，遵循固定步骤：(1) protocol.go 新增 Method 和 Request 类型 → (2) server.go 实现 handler → (3) client.go 实现客户端方法 → (4) cmd/rnix 实现 CLI。这个步骤已经足够标准化，可以作为编码规范文档化。

3. **环形缓冲区是"每步记录"数据的正确选择** — Process.tokenHistory（15-5）和 Process.logHistory（已有）都使用了环形缓冲区。对于需要在 reasonStep 热路径中记录但只保留最近 N 条的数据，环形缓冲区是最佳方案：O(1) 写入、固定内存、无 GC 压力。

4. **NFR 性能约束驱动了更好的设计** — NFR33（Trace 传播 < 10ms）推动了"零开销旁路"设计（`if proc.TraceID != ""` 守卫）；NFR34（ctx-profile 分析 ≤ 1s）推动了 `context.WithTimeout` 保护。性能约束不是负担，而是设计的指南针。
