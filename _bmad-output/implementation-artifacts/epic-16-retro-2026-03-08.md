### 业务成果

Epic 16 为 Rnix 构建了完整的声明式推理回归测试框架（agtest），实现从"定义→评估→执行→报告"的端到端流程：

**测试定义层（Story 16.1）：**
- YAML 声明式测试用例格式（version 1.0），支持单文件和多用例套件
- 自动格式检测（有 `tests` 键 → 套件，无 → 单用例自动包装）
- 带行号的校验错误报告（通过 goccy/go-yaml AST 提取位置信息）
- `rnix agtest --dry-run` 仅解析校验，不执行

**断言评估层（Story 16.2）：**
- 三维断言覆盖：输出断言（contains/not_contains）、syscall 断言（includes/excludes）、质量断言（LLM-as-judge）
- QualityJudge 接口抽象，允许 mock 和真实 LLM 实现
- 统一 AssertionResult 结构（Type/Passed/Message/Expected/Actual）

**执行与报告层（Story 16.3）：**
- TestExecutor 接口解耦 agtest 包与 ipc 依赖
- 通过 IPC daemon 执行测试（SpawnAndWatch），syscall 通过 AttachDebug 二次连接收集
- ParseQualityResponse 三级 fallback（标准 JSON → markdown fence JSON → 启发式）
- 纯文本（✓/✗）和 JSON（JSONResponse 包装）双格式报告
- 失败时 exit code = 1，便于 CI 集成

## 成功与优势

1. **三层渐进构建零返工** — 16-1 建立类型和解析基础设施，16-2 在此之上实现断言评估逻辑，16-3 整合执行和报告。三个 story 之间的接口严格通过 `*AssertConfig`（指针，nil 安全）和 `TestResult` 结构体连接，每层只做自己的事。16-1 预留的 AssertConfig 指针在 16-2 中无缝对接，16-2 的 EvalAssertions 在 16-3 中被直接调用，零回看修改。

2. **compose/ 三层解析模式的成功复用** — agtest 的 ParseFile/ParseBytes/validate 三层模式完整复制了 compose/ 的设计。这不是偶然——Epic 7（Compose）建立的 YAML 解析模式已经成为项目的"基础设施模式"，在 agtest 中的第二次验证进一步确认了其通用性。两个包使用相同的 goccy/go-yaml 库、相同的解析流程、相同的 testdata 目录结构，但代码完全独立，没有不当耦合。

3. **TestExecutor 接口设计精妙** — 16-3 的最大架构亮点是 TestExecutor 接口的引入。这个接口使 agtest 包完全不依赖 ipc 包，IPC 实现（ipcExecutor）被推到 cmd/rnix 层。结果是：agtest 包的 72 个测试全部使用 MockExecutor 运行，不需要启动 daemon、不需要 mock IPC client，测试速度极快且 100% 确定性。这是"依赖倒置"原则的教科书级应用。

4. **零新增 IPC 方法** — 与 Epic 13-15 每个 Epic 都新增 IPC 方法不同，Epic 16 完全复用了已有的 MethodSpawn（通过 SpawnAndWatch）。agtest 本质上只是一个智能的 spawn 编排器：解析 YAML → 构造 SpawnRequest → 执行 → 收集结果 → 评估断言。这个"复用而非扩展"的策略大幅降低了实现复杂度和维护成本。

5. **QualityJudge 接口与 ParseQualityResponse fallback 的务实设计** — 质量断言面临的核心挑战是 LLM 输出格式不可控。16-3 的 ParseQualityResponse 实现了三级 fallback：先尝试标准 JSON 解析，失败则提取 markdown code fence 内的 JSON，再失败则用启发式（搜索 `"passed": true`）。这不是过度工程，而是对 LLM 输出不确定性的务实应对。同时 QualityJudge 接口使单元测试可以完全 mock，集成测试时切换到真实 LLM。

6. **新建顶级包 agtest/ 的干净架构** — agtest/ 是项目第一个纯"用户空间"工具包（不属于 kernel、vfs、debug、ipc 任何层），它的依赖关系极简：只依赖标准库 + goccy/go-yaml（解析）和 context（QualityJudge 接口），不导入项目其他包。这与 compose/、agents/ 的独立包模式一致，验证了项目的"扁平包结构"设计。

7. **零新增外部依赖** — 三个 story 全部使用项目已有的 goccy/go-yaml、spf13/cobra、标准库。对于一个新功能域（测试框架），能做到零外部依赖增长，说明项目的依赖管理非常克制。

## 挑战与成长领域

1. **AttachDebug syscall 收集的发现过程** — 16-3 的 Dev Notes 最初设计是从 SpawnAndWatch 的 onEvent 回调中直接收集 StreamSyscallEvent。但实现中发现 spawn 流不包含 syscall 事件（handleSpawn 不发送 syscall_event），需要启动独立 goroutine 通过 AttachDebug 二次连接收集。这个发现说明对 IPC spawn 流的事件内容假设需要在 create-story 阶段更仔细地验证。

2. **Epic 16 的 Story 规模差异较大** — 16-1 有 6 个 Task（28 个测试），16-2 有 7 个 Task（35 个测试），而 16-3 有 6 个 Task（19 个测试）但 CLI 修改更复杂（ipcExecutor、ipcQualityJudge、双格式报告）。16-3 的实际复杂度更高但 Task 数量更少，因为它是集成层——多个组件的编排比单个组件的实现更难估算。

3. **CLI 测试仍然以 mock 为主** — 与 Epic 14-15 延续的技术债一致，agtest CLI 的 8 个测试主要验证报告格式和参数解析，使用 mock runner 而非真实 daemon。虽然 agtest 包的 72 个单元测试覆盖了核心逻辑，但 CLI → IPC → Kernel → LLM 的完整路径没有自动化验证。

4. **质量断言依赖 LLM 响应格式** — ipcQualityJudge 通过构造 intent prompt 请求 LLM 返回 JSON，但 LLM 的输出格式本质不可控。虽然 ParseQualityResponse 有三级 fallback，但这是一种补偿性设计，不是根本解决方案。未来可考虑使用 structured output（如 tool_use response）获得更可靠的 JSON。

5. **无测试结果持久化** — 当前 agtest 只做实时报告，不缓存结果。对于 CI 集成场景，可能需要将测试结果持久化到 `.rnix/tests/` 以支持趋势分析和历史对比。这在 16-3 的"不要做"清单中已明确排除，但作为后续增强值得记录。

## 关键洞察

1. **"复用而非扩展"是最优策略** — Epic 16 证明了一个成熟的系统不需要为每个新功能添加新的基础设施。agtest 完全复用了 MethodSpawn（IPC）、SpawnAndWatch（客户端）、goccy/go-yaml（解析）、Cobra（CLI），只新增了属于自己的领域逻辑（解析/校验/评估/运行）。这是架构成熟度的标志：基础设施层足够通用，新功能只需组合而非重建。

2. **接口抽象的"推迟到使用者"模式** — TestExecutor 接口定义在 agtest 包中（使用者），而不是 ipc 包中（提供者）。这遵循了 Go 的 "accept interfaces, return structs" 原则和依赖倒置原则。结果是 agtest 包可以独立测试、独立编译，与 ipc 包之间是弱依赖（duck typing）而非强依赖。这个模式应该被推广到项目其他需要解耦的场景。

3. **ParseFile → ParseBytes → Validate 三层模式已成为项目标准** — compose/ 首创，agtest 第二次验证。该模式的核心价值是：ParseFile 处理 I/O，ParseBytes 处理反序列化（纯函数，易测），Validate 处理业务校验（可独立调用）。三个关注点分离干净，每层都可以独立测试。建议在 project-context.md 中文档化为"YAML 解析标准模式"。

4. **LLM-as-judge 是一个值得独立抽象的模式** — 质量断言的 QualityJudge 接口揭示了一个通用需求：让 LLM 评估另一个 LLM 的输出。这不仅适用于 agtest，也可能适用于未来的自动代码审查、文档质量评估等场景。当前 ipcQualityJudge 硬编码在 cmd/rnix 中，如果这个模式被更多场景使用，值得提取为独立的 `judge/` 包。
