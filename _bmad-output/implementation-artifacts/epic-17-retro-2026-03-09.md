### 业务成果

Epic 17 为 Rnix 构建了统一的全屏可视化调试面板，将智能体树、syscall 时间线、上下文热力图三个视角整合在一个交互式 TUI 中，支持实时监控和离线回放分析。这是 Phase 3（可观测性工具链）的收官之作。

**框架层（17-1）：** 建立了 bubbletea v2 全屏 TUI 应用的完整架构模式——Model/Init/Update/View 三件套、500ms tick 轮询、多窗格 lipgloss 布局、虚拟滚动、键盘路由分层。这是项目首次大规模使用 bubbletea，为后续 TUI 功能奠定了基础。

**数据层（17-2 + 17-3）：** 实现了两种不同的数据获取模式：时间线使用 AttachDebug 流式订阅（实时事件推送），热力图使用 CtxProfile 周期轮询（每 2.5s 请求-响应）。两种模式都通过独立 IPC 连接隔离，不干扰主 tick 循环。

**交互层（17-4）：** 消除了窗格联动的 500ms 感知延迟（从 tick 驱动改为即时触发），引入了 `tea.ExecProcess` 暂停/恢复模式实现 gdb 和 log 的无缝集成。

**回放层（17-5）：** 复用了 dashboard 的全部渲染逻辑，仅通过 `replayMode` 条件分支切换数据来源——从 IPC 流改为 RecordReader 本地文件。实现了完整的回放控制（播放/暂停/调速/逐帧/跳转），且不需要 daemon 运行。

## 成功与优势

1. **渐进式窗格构建，零回看修改** — 17-1 的框架设计预留了 `paneType` 常量、`activePane` 字段和 `renderDashboardPlaceholder` 占位函数。17-2 和 17-3 分别替换占位函数，17-4 在此基础上添加联动，17-5 复用全部渲染逻辑。整个过程中框架代码几乎没有被回头修改，说明 17-1 的架构设计前瞻性很好。

2. **零新增 IPC 方法 + 零新增外部依赖 + 零新增包** — 连续第二个 Epic 实现了"极简增量"。dashboard 完全复用了 `ListProcs`（进程列表）、`Kill`（进程终止）、`AttachDebug`（事件流）、`CtxProfile`（上下文分析）、`RecordStart/Stop`（录制控制）等已有 IPC 方法。所有代码集中在单个文件 `dashboard.go` 中，与 `top.go` 模式一致。这再次验证了 Rnix 基础设施层的通用性。

3. **IPC 连接隔离策略成熟** — 17-2 发现 AttachDebug 流式订阅不能与主 tick 的 ListProcs 共用连接（共享 scanner），于是引入"每功能独立 Dial"模式。17-3 的 CtxProfile 和 17-4 的 RecordStart/Stop 延续了这一策略。这个模式已经成为 dashboard 类多数据源 TUI 的标准做法。

4. **bubbletea v2 API 知识快速积累** — 17-1 是项目首次全屏 TUI 开发，通过分析 `top.go` 的 v2 用法（`tea.View`、`tea.NewView`、`tea.KeyPressMsg` 的 `Code`/`Mod` 字段）建立了 v2 工作模式。到 17-4 引入 `tea.ExecProcess`（暂停 TUI 运行子进程），17-5 实现完整回放控制，团队对 bubbletea v2 的掌握已经非常熟练。

5. **Code Review 发现模式一致且修复彻底** — 5 个 Story 的 Code Review 共发现约 20 个问题（5 HIGH、8 MEDIUM、7 LOW），所有 HIGH 和 MEDIUM 问题都在同一 story 内修复。最常见的问题类型是"渲染逻辑遗漏"（状态未着色、列缺失、键未处理），这暗示 TUI 开发中视觉完整性验证是持续挑战。

6. **回放模式设计优雅** — 17-5 通过 `replayMode bool` 一个字段将 dashboard 从"实时监控"切换为"离线回放"，复用了 tree/timeline/heatmap 的全部渲染逻辑，只替换数据来源。这种"数据源抽象 + 渲染复用"的分离策略使回放功能的实现量大幅减少。

7. **纯函数设计贯穿始终** — `buildProcessTree`、`flattenTree`、`classifySyscall`、`buildHeatmapSegments`、`recordEventToWire`、`loadReplayTimeline`、`buildReplayHeatmap` 等核心逻辑都是纯函数，易于测试且无副作用。~85 个测试中大部分是对这些纯函数的直接验证。

## 挑战与成长领域

1. **Code Review 持续发现渲染遗漏** — 每个 Story 的 Code Review 都发现了 HIGH 级别的渲染/交互遗漏：17-1 缺进程状态着色和 Skills 列、17-2 缺 IPC 流接入和 filter 初始化、17-3 缺 enter 键处理和 tool 合并、17-4 的键冲突排除、17-5 的 vim 导航键误屏蔽。这说明 TUI 开发中"交互完整性"比"逻辑正确性"更容易遗漏。建议在 story Dev Notes 中增加"交互检查矩阵"——对每个快捷键在每个窗格的预期行为做明确声明。

2. **dashboard.go 文件体积膨胀** — 5 个 Story 的所有逻辑集中在 `cmd/rnix/dashboard.go` 一个文件中（包含模型定义、Init/Update/View、3 个窗格渲染、键盘路由、IPC 交互、回放逻辑），估计已超过 1000 行。虽然与 `top.go` 单文件模式一致，但 dashboard 的复杂度远超 top。如果后续有 dashboard 增强需求，可能需要考虑拆分（如 `dashboard_tree.go`、`dashboard_timeline.go` 等）。

3. **17-2 Story 状态同步不一致** — sprint-status.yaml 中 17-2 已标记 `done`，但 Story 文件头部仍显示 `Status: review`。这是文件状态未同步的问题，虽然不影响功能，但对于自动化状态追踪可能造成混淆。

4. **键盘路由复杂度随窗格增长呈指数增长** — 17-4 的最大挑战是全局操作键（k/a/l/r）与窗格特定键（tree 的 k=导航、timeline 的 l=右滚）的冲突解决。最终通过 `isPaneNavConflict` 排除实现，但这种"排除法"在未来添加更多窗格或快捷键时会越来越脆弱。更好的方案是引入显式的"键绑定注册"机制。

5. **热力图数据精度受限** — 17-3 的热力图依赖 `CtxProfile` 返回的 `TopConsumers`（前 5 个消费者），这意味着超过 5 种来源的上下文分布会被合并。17-5 的回放热力图更粗糙——从 `ContextSnapshotData` 的消息前缀推导来源分类，是一个近似方案。这是现有 IPC API 设计的限制，不是 dashboard 的问题。

6. **回放模式的速率模型是简化版** — 17-5 使用"每 tick N 个事件"的离散步进模型，而非基于真实时间间隔的回放。这在事件间隔不均匀时会导致回放节奏失真。Dev Notes 中已明确记录了这个取舍（500ms tick 下真实时间模拟效果不佳），属于有意识的简化而非疏忽。

## 关键洞察

1. **"单文件 TUI 命令"模式的规模边界** — `top.go`（~200 行）和 `dashboard.go`（~1000+ 行）表明，单文件模式在 3 个窗格以内可控，超过后维护成本显著上升。项目应明确"TUI 命令单文件上限"——建议以 500 行为软上限，超过后按窗格拆分为同包子文件。

2. **异步数据获取的"三模式"已形成** — tick 轮询（ListProcs）、流式订阅（AttachDebug）、按需请求（CtxProfile）三种 IPC 交互模式在 dashboard 中全部出现并被验证。每种模式都有明确的使用场景和 bubbletea 集成方式，这是 TUI 数据获取的完整工具箱。

3. **`tea.ExecProcess` 是 TUI 与交互式工具集成的关键桥梁** — 17-4 证明了在 bubbletea 全屏应用中可以无缝"暂停→运行子进程→恢复"。这打开了 dashboard 作为"统一操作入口"的可能性——用户无需退出 dashboard 即可调用 gdb、查看 log、执行 strace。

4. **"replayMode bool"是条件分支隔离的极简范例** — 17-5 用一个 bool 字段将整个 dashboard 从实时切换到回放，复用所有渲染逻辑，只替换数据来源。这个模式可以推广到其他"双模式"场景（如 mock 模式、demo 模式）。

5. **FIFO 缓冲 + 虚拟滚动是 TUI 性能保障的双保险** — timeline 的 1000 条事件 FIFO 限制 + 树窗格的虚拟滚动（只渲染可见行）共同确保了 NFR36（500ms 刷新）和 NFR37（50 进程无卡顿）。这两种技术应该成为未来 TUI 功能的标配。

## Epic 18 准备度评估

### Epic 18: AgentShell 完整脚本语言

**概要：** 5 个 story — 循环结构与内置命令、函数定义与调用、数据结构与字符串插值、Spawn 返回值捕获与并行执行、模块化与脚本执行

**对 Epic 17 的依赖分析：**

| 依赖项 | 状态 | 风险 |
|--------|------|------|
| 基础 AgentShell 语法（Epic 11：变量/管道/控制结构） | ✅ 稳定 | 低 — 18 在 11 基础上扩展 |
| Spawn/Kill/Wait syscall | ✅ 稳定 | 低 — 18-4 的返回值捕获依赖 Spawn |
| 进程组和并行模型（Epic 6） | ✅ 稳定 | 低 — 18-4 parallel 块可能使用进程组 |
| Dashboard（Epic 17） | ✅ 无直接依赖 | 无 — AgentShell 不依赖 dashboard |
| agtest（Epic 16） | ⚠️ 间接关联 | 低 — agtest 可用于验证 AgentShell 脚本行为，但不是硬依赖 |

**技术领域差异：**

Epic 18 与 Epic 17 的技术领域完全不同——从 TUI 渲染转向语言解析器/解释器实现。关键挑战：

| 准备项 | 优先级 | 描述 |
|--------|--------|------|
| 现有 AgentShell 解析器架构审查 | 关键 | Epic 11 实现了基础语法（管道/变量/if-else），需要审查现有 AST 结构和解释器设计，确定循环/函数/数据结构如何扩展 |
| 词法分析器扩展评估 | 关键 | 新增 `for`/`while`/`fn`/`return`/`parallel`/`source` 关键字，评估现有词法分析器的扩展难度 |
| 作用域管理设计 | 重要 | 函数定义引入局部作用域、`source` 引入模块作用域，需要设计作用域链（scope chain）机制 |
| 并行执行模型设计 | 重要 | `parallel { ... }` 块需要批量 Spawn + 聚合等待，需要决定是使用进程组还是独立等待 |
