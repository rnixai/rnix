### 业务成果

Epic 18 将 AgentShell 从 Phase 2 的基础语法（管道/变量/if-else）扩展为完整的脚本语言，支持循环、函数、数据结构、并行执行和模块化。这是 Phase 3 中唯一的语言基础设施 Epic，为后续 Epic 19（声明式意图）和 Epic 20（自主智能体）的编排能力提供了脚本层支撑。

**语法层（18.1 + 18.2）：** 建立了 `for`/`while` 循环和 `fn`/`return` 函数的完整 AST 节点和递归下降解析模式。所有块级结构统一使用 `end` 终止符，保持语法一致性。`ErrScriptExit` 和 `ErrFnReturn` 的错误传播模式形成了 AgentShell 的流控制框架——错误作为流控制信号向上传播，在特定层捕获。

**数据层（18.3）：** Environment 从单一 `map[string]string` 扩展为三并行 map 架构（vars/arrays/maps），通过类型互斥规则（同名 key 只存在于一个 map）保证一致性。`ExpandStrict` 的引入让 spawn intent 中的未定义变量从"静默替换为空"变为"报错含行号"，显著提升了脚本调试体验。

**并行层（18.4）：** 三阶段并行执行模型（顺序展开→goroutine 并行执行→顺序收集）解决了 Environment 非线程安全的核心约束。intent 预展开确保 env 读取在单线程中完成，goroutine 仅调用线程安全的 KernelSpawner 接口。

**模块层（18.5）：** `source` 语句和 `rnix run` 命令将 AgentShell 从"内联脚本"提升为"文件系统中的独立程序"。FileReader 接口的引入是 shell 包首次使用依赖注入实现可测试性（之前只有 KernelSpawner）。

## 成功与优势

1. **渐进式解析器扩展，零架构回退** — 5 个 Story 逐步扩展同一个递归下降解析器：18.1 新增 for/while，18.2 新增 fn/return，18.3 新增数据结构赋值和内置函数，18.4 新增 parallel 块，18.5 新增 source。每个 Story 遵循完全相同的模式：新增 StatementKind → 新增 AST 结构体 → 扩展 parseBlock → 扩展 executeBlock → 扩展 validateFnCalls → 扩展 countStagesInBlock。整个过程中前序 Story 的代码几乎没有被修改，说明 Decision 10（手写递归下降解析器）的架构决策在复杂度增长下依然稳健。

2. **零调试循环 × 5 个 Story** — 所有 5 个 Story 的实现记录均显示"一次通过"或"所有测试一次性通过"。这在 22 个 Epic 的项目历史中极为罕见。主要归因于：(a) ATDD 测试先行，红→绿驱动；(b) 每个 Story 的 Dev Notes 极其详尽，包含语法示例、解析伪代码、执行流程图、组合矩阵；(c) 技术领域（解析器/解释器）的确定性高于 TUI/IPC 等领域。

3. **Code Review 质量始终在线** — 5 个 Story 共发现 21 个 CR 问题（6H + 10M + 5L），**全部在同一 Story 内修复**。HIGH 问题的模式一致：错误消息缺失关键信息（行号、标识符）、输入校验遗漏（len 对未定义变量静默返回 0）、测试覆盖缺口（shebang 测试）。CR 持续发现真正影响用户体验的问题，证明了双人 review 的价值。

4. **保留关键字预注册策略成功** — 18.1 在实现 for/while 时，就将 Phase 3 所有 10 个关键字（for/in/while/fn/return/parallel/source/wait/sleep/exit）全部注册为保留字。这确保了 18.2 实现 fn/return、18.4 实现 parallel、18.5 实现 source 时，不会出现用户已定义同名变量的冲突。这种前瞻性设计值得推广到其他需要渐进式扩展的系统中。

5. **错误传播模式的一致性演进** — 从 18.1 的 `ErrScriptExit`（exit 命令的流控制）到 18.2 的 `ErrFnReturn`（return 的流控制），团队建立了"错误类型作为流控制信号"的统一模式：定义 error 类型 → 在特定层 `errors.As` 捕获 → 清除 error → 提取值。18.4 的 parallel 块虽然不使用 error 作为流控制，但结果收集模式（预分配 slice → goroutine 写自己的索引 → 主 goroutine 顺序读取）同样体现了一致的设计哲学。

6. **shell 包自包含性** — 18.1～18.4 的所有改动完全限制在 `shell/` 包内，无需修改 kernel/vfs/drivers/cmd。18.5 是唯一跨包的 Story（新增 `cmd/rnix/run.go` 和修改 `ipc/protocol.go`），但影响范围仍然可控。这验证了 Rnix 的分层架构——语言层与内核层通过 KernelSpawner 接口干净隔离。

7. **测试策略成熟** — ~171 个新增测试覆盖了解析、执行、组合、竞态四个维度。18.4 引入了 `concurrentMockSpawner`（线程安全 mock），是 shell 包首次支持并发测试。18.5 引入了 `mockFileReader`，是 shell 包首次使用 IO mock。测试基础设施在 Epic 过程中持续增强。

## 挑战与成长领域

1. **script.go 文件规模失控** — 与 Epic 17 的 `dashboard.go` 膨胀问题一致，Epic 18 的 `shell/script.go` 承载了全部 AST 定义、解析器逻辑、解释器逻辑、校验逻辑、复杂度统计。经过 5 个 Story 的扩展，该文件预估超过 1500 行。parseBlock 函数的关键字检测链已增长到 10 个分支（end/fn/return/if/parallel/for/while/source/builtin/parseStatement），executeBlock 的 switch 也有类似膨胀。18.5 意识到了这个问题（将 FileReader/OSFileReader 拆到 `file_reader.go`），但核心逻辑仍在单文件中。

2. **Code Review 发现的 HIGH 问题类型趋同** — 6 个 HIGH 问题的模式高度一致：(a) 错误消息缺失信息（18.1 exit 校验范围、18.2 行号缺失）；(b) 输入校验遗漏（18.3 len 对 undefined 静默返回 0、18.3 map key 校验）；(c) 测试覆盖缺口（18.4 while 测试用错误语法、18.5 shebang 测试缺失）。这三类问题反复出现，说明开发过程中有系统性的盲区——可能是"快乐路径优先"的开发习惯，对异常输入和边界情况关注不足。

3. **validateFnCalls 的 source 降级** — 18.5 为处理 `source` 引入的运行时函数注册问题，在 `validateFnCalls` 中增加了 `hasSource` 参数：当脚本含 source 语句时，跳过未定义函数的静态检查。这意味着 source 后调用不存在的函数只会在运行时报错，丧失了静态校验的优势。这是一个有意识的简化决策，但如果 AgentShell 脚本规模增长，缺乏静态分析会成为问题。

4. **CLI E2E 测试持续缺失** — 这已经是连续第六个 Epic 提到 CLI E2E 测试薄弱。18.5 新增的 `rnix run` 命令有 6 个测试，但都是命令注册和参数校验级别的"浅测试"，没有实际运行脚本的端到端验证。整个 shell 包的 ~171 个测试全部是单元/ATDD 级别，依赖 mock spawner。

5. **Environment 并行 map 方案的扩展性隐忧** — 18.3 选择三并行 map（vars/arrays/maps）而非 `map[string]interface{}` 的方案，优势是零修改现有接口。但随着数据类型可能增加（如嵌套结构、set 类型），每新增一个类型就需要新增一个 map + 对应的 Get/Set 方法 + 类型互斥清除逻辑。当前三种类型可管理，但方案缺乏长期扩展性。

6. **并行 mock 测试的正确性依赖** — 18.4 的并行测试使用 `concurrentMockSpawner` 验证并行执行，但 mock spawner 的 SpawnAndWait 是即时返回的，没有模拟真实的 LLM 延迟。这意味着并行执行的时序特性（如竞争条件、超时行为）没有被充分测试。`-race` 检测覆盖了数据竞争，但不覆盖逻辑时序问题。

## 关键洞察

1. **"语句类型 × 6 步扩展"是解析器增量开发的可靠模式** — 每个新语法特性的实现遵循固定六步：(1) StatementKind 常量 (2) AST 结构体 (3) parseBlock 关键字检测 (4) executeBlock case 分支 (5) validateFnCalls 分支 (6) countStagesInBlock 分支。这个模式在 5 个 Story 中被反复验证，应该文档化为"AgentShell 语法扩展清单"。

2. **"错误类型作为流控制"是 AgentShell 的核心架构模式** — `ErrScriptExit`（终止脚本）、`ErrFnReturn`（函数返回）形成了两层流控制。这种模式使得 return 可以穿透 for/while/if 嵌套直达函数调用处，exit 可以穿透所有嵌套直达 Execute 顶层。这是 AST walker 解释器的经典做法，值得记录为架构决策。

3. **三阶段并行模型是单线程解释器支持并发的正确方案** — "顺序展开 → goroutine 并行执行 → 顺序收集"完美绕过了 Environment 非线程安全的约束。关键洞察是：所有需要读/写共享状态（env/captures）的操作在主 goroutine 中完成，goroutine 仅调用线程安全的外部接口（KernelSpawner）。这个模式可以推广到其他需要"在非线程安全上下文中引入并行"的场景。

4. **ATDD 测试先行是零调试循环的关键因子** — 5 个 Story 全部零调试循环，与 ATDD（Acceptance Test Driven Development）方法直接相关。ATDD 测试在 create-story 阶段预写（RED），dev-story 阶段实现使其变 GREEN。这确保了开发者从第一行代码就有明确的目标和即时反馈。

5. **保留关键字预注册 + 类型互斥规则 = 防御性设计的两个典范** — 保留关键字预注册防止了"用户已使用未来关键字作为变量名"的兼容性灾难。类型互斥规则（Set 清除同名 array/map）防止了"同一变量名在不同类型间切换"导致的幽灵状态。这两种模式都是"通过约束简化复杂度"的范例。

| 依赖项 | 状态 | 风险 |
|--------|------|------|
| AgentShell 脚本语言（Epic 18） | ✅ 完整 | 低 — Reconciler 可能使用 AgentShell 脚本编排子任务，但不是硬依赖 |
| Spawn/Kill/Wait syscall | ✅ 稳定 | 低 — 意图分解后的子任务通过 Spawn 执行 |
| 进程组和信号系统（Epic 6） | ✅ 稳定 | 低 — Reconciler 可能使用进程组管理子任务集 |
| IPC 协议（贯穿多个 Epic） | ✅ 稳定 | 低 — `rnix apply` 和 `rnix intent status` 需新增 IPC 方法 |
| 上下文管理（Epic 1） | ✅ 稳定 | 中 — 意图树可能需要独立的上下文生命周期管理 |

**技术领域差异：**

Epic 19 与 Epic 18 的技术领域完全不同——从语言解析器/解释器转向状态管理/事件驱动系统。关键挑战：

| 准备项 | 优先级 | 描述 |
|--------|--------|------|
| Intent 数据模型设计 | 关键 | 意图树（Intent Tree）的数据结构设计——节点类型、状态机（Desired/Current/Drift）、依赖关系图。这是全新领域，无现有代码可参考 |
| Reconciler 架构设计 | 关键 | 事件驱动 Reconciler 的触发机制——进程退出事件 → 状态更新 → 依赖检查 → 新任务启动。需要决定是轮询模式还是事件订阅模式 |
| `rnix apply` CLI 设计 | 重要 | 与现有 `rnix -i` 和 `rnix run` 的关系——`rnix apply` 是高层意图，`rnix -i` 是直接 spawn，需要明确各命令的定位和交互 |
| LLM 用于意图分解 | 重要 | 意图分解依赖 LLM 将高层意图拆解为子意图树。需要设计 prompt 模板和输出解析（JSON schema） |
| NFR40 性能基准（drift 检测 ≤ 5s） | 重要 | Reconciler 的事件处理延迟需要满足 5 秒内启动调和行动 |

**无重大发现需要更新 Epic 19 计划。** Epic 18 的 AgentShell 脚本语言与声明式意图是互补功能域——AgentShell 提供显式编排（用户写脚本），Intent 提供隐式编排（用户声明目标）。两者不冲突，但 Reconciler 可能使用 AgentShell 作为子任务编排的底层机制。
