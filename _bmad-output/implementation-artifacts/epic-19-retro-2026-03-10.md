### 业务成果

Epic 19 为 Rnix 引入了声明式意图编排层——用户仅需说出"我要一个完整的博客系统"，系统自动分解为子任务 DAG 并调度执行。这是从"显式编排"（用户手写 compose YAML 或 AgentShell 脚本）到"隐式编排"（用户声明目标，系统自主规划）的关键跃迁。

**意图基础设施（19.1）：** 建立了完整的声明式意图系统——IntentTree 数据模型、LLM 驱动的任务分解、事件驱动执行引擎、IPC 流式协议、CLI 命令。独立的 `intent/` 包遵循了严格的依赖方向规则（不导入 kernel/cmd/ipc），通过接口抽象（LLMCaller、KernelSpawner）实现可测试性。

**自动调和（19.2）：** Reconciler 将简单的一次性执行器升级为自修复系统——失败自动重试、超时自动处理、drift 持续跟踪。事件驱动的 channel-based 架构确保 NFR40（drift 到调和启动 ≤5s）自然满足。三态模型（Desired/Current/Drift）借鉴了 Kubernetes 的声明式理念，但采用了更轻量的事件驱动而非轮询模式。

**动态调整（19.3）：** 增量合并机制让用户可以在执行过程中动态扩展需求——新增节点不影响已完成工作，修改节点自动重执行。MergeIncremental 是纯函数设计，合并失败时自动回滚。Reconciler.InjectNodes 通过共享 mutex 实现运行时安全注入。

## 成功与优势

1. **完整的 intent/ 包从零构建，架构干净** — intent 包包含 7 个核心文件（types/dag/decomposer/cli_caller/engine/reconciler/merge/manager），依赖方向严格单向（intent/ → types/，ipc/ → intent/ 通过接口），不直接导入 kernel/cmd/ipc。LLMCaller 和 KernelSpawner 两个核心接口确保了所有外部依赖可 mock。这是 Rnix 继 compose/ 之后的第二个完全独立的编排子系统，证明了"接口隔离 + 适配器模式"在跨层通信中的有效性。

2. **Engine → Reconciler 渐进式增强，零架构回退** — 19.1 构建 Engine（简单一次性执行），19.2 在 Engine 基础上构建 Reconciler（增加重试/超时/drift），19.3 为 Reconciler 添加 InjectNodes（运行时注入）。整个过程中 Engine 代码零修改并保留可用。Reconciler 采用与 Engine 相同的事件驱动模式（channel + goroutine），架构一致性极高。每个 Story 的增量扩展都不破坏前序 Story 的代码，说明 19.1 的基础设计考虑了后续扩展。

3. **Code Review 持续发现有价值的问题** — 19.1 的 CR 发现 apply.go 确认流程中 intentID 为空的关键缺陷（从 decomposed 事件提取而非依赖返回值），以及 handleApplyIntent 需使用原始 connScanner 的并发安全问题。19.2 的 CR 发现 IntentRetrying 状态为死代码、finalizeTreeState 未设置 CompletedAt、ComputeDrifts 将 pending 节点误归类为 timeout drift 等 4 个 MEDIUM 问题。所有问题均在同一 Story 内修复，CR 质量稳定。

4. **事件驱动 Reconciler 设计精妙** — 与 Kubernetes 的轮询式 Reconciler 不同，Rnix 选择了事件驱动模式（Go channel）。核心观察：Rnix 的 intent 节点是有限数量的离散任务，不需要 K8s 级别的声明式资源管理。channel 事件消费是纳秒级操作，NFR40（≤5s）自然满足。这个设计决策体现了对问题域的深刻理解——不照搬知名框架模式，而是根据实际需求选择最合适的方案。

5. **MergeIncremental 纯函数设计 + 验证后合并** — 增量合并的核心设计是"先验证，后合并"——MergeIncremental 先验证所有新节点的依赖有效性和 DAG 无循环，验证通过后才修改 IntentTree。验证失败时自动回滚（不修改原树）。这种防御性设计确保了运行中的意图树不会因为无效的增量更新而进入不一致状态。

6. **IPC 流式协议一致性** — 4 个新 IPC 方法严格遵循项目已有的 IPC 扩展标准步骤：Method 常量 → Request/Response 类型 → Wire 类型 → Server handler → Adapter → Client 方法 → CLI 命令。所有新增 JSON 字段使用 snake_case，StreamEvent 类型使用 `StreamIntent` 前缀 + PascalCase。19.1 建立的 `syncWriteEvent` 并发写保护模式在 19.2 和 19.3 中被复用。

7. **测试覆盖全面，100+ 个新测试** — intent 包的测试覆盖了类型方法、DAG 构建/循环检测/拓扑排序、分解器成功/失败/超时、引擎串行/并行/级联失败、Reconciler 重试/超时/drift/NFR40 延迟验证、合并新增/修改/未变化/无效依赖/循环依赖等场景。UI 测试覆盖了 TTY/JSON/Quiet 三种输出模式。所有测试 `-race` 通过。

## 挑战与成长领域

1. **19.2 调试循环：Timeout 测试 mock spawner 的 context 取消** — TestReconciler_Execute_Timeout 最初失败，因为 mock spawner 的 Wait 不尊重 context 取消，导致超时检测无法触发。修复方案是将 Wait 调用移至独立 goroutine，通过 select 同时监听 waitCh 和 nodeCtx.Done()。这个问题暴露了一个普遍性挑战：mock 对象需要精确模拟真实对象的 context 取消行为，否则并发控制测试会失败。

2. **IPC intentManager 接口膨胀** — 从 19.1 到 19.3，`intentManager` 接口从 5 个方法增长到 7 个方法，其中 `ExecuteIntent` 的签名从 4 个回调参数增长到 8 个。19.2 的 CR 注意到这种趋势但未做优化（功能优先）。如果 intent 系统继续扩展（如持久化、权限控制），接口可能需要重构为回调结构体或分拆为多个细粒度接口。

3. **19.3 Story 文件 Status 字段不一致** — Story 19.3 的文件头 Status 标记为 "review"（不是 "done"），但 sprint-status.yaml 中已标记为 done。这是 Epic 18 回顾中已发现的"Story 文件状态同步"问题的再次出现。建议在 dev-story 完成后统一更新 Status 字段。

4. **增量分解 Prompt 的 LLM 依赖风险** — 19.3 的增量分解依赖 LLM 输出完整的合并后任务列表（包含已有+新增节点），然后由 MergeIncremental 做差异计算。虽然确定性合并逻辑降低了 LLM 输出不确定性的风险，但如果 LLM 不正确地修改了已有节点的 ID 或 intent，合并结果可能不符合用户预期。当前没有"用户确认增量合并结果"的步骤（不像 apply 有确认步骤）。

5. **intent 包内存管理** — IntentTree 仅存在于内存，所有 3 个 Story 都明确标注"意图持久化不在范围内"。随着 Epic 20 引入 OODA 循环和自主智能体，长时间运行的意图树可能消耗显著内存。activeReconcilers map 没有清理机制（Reconciler 完成后不从 map 中移除），可能导致内存泄漏。

6. **CLI E2E 测试持续缺失（第七个 Epic）** — 19.1 新增的 rnix apply/intent status 的测试仍为 Cobra 注册级别的"浅测试"，没有实际运行 apply 命令的端到端验证。19.3 新增的 rnix intent list 也是同样模式。这已经是从 Epic 14 延续至今第七个 Epic 的未解决问题。

## 关键洞察

1. **"接口隔离 + 适配器"是跨层通信的最佳模式** — intent/ 包通过 LLMCaller 和 KernelSpawner 两个接口完全隔离了外部依赖，ipc/ 层通过 IntentManagerAdapter 适配 intent.Manager 到 intentManager 接口。这种三层架构（核心逻辑 → 接口 → 适配器）使得 intent 包的 100+ 个测试完全不依赖 IPC/kernel/daemon，极大提升了测试速度和可靠性。这是 Rnix 项目中"VFS 设备抽象"和"compose KernelSpawner"模式的再次验证。

2. **事件驱动 > 轮询，当事件源是有限离散的** — Reconciler 选择 channel 而非轮询是正确的。关键判断标准：事件源数量（intent 节点数通常 < 100），事件类型数量（3 种：completed/failed/timeout），事件延迟要求（≤5s）。这些参数明确指向事件驱动模式。对比 K8s 的 informer + work queue 模式（适用于大规模持续观察），Rnix 的场景不需要那种复杂度。

3. **"先验证后合并"是不可变数据结构修改的安全模式** — MergeIncremental 的设计模式——先在临时状态中验证依赖有效性和 DAG 无循环，验证通过后才修改原始 IntentTree——可以推广到所有需要"安全修改运行时状态"的场景。这比"修改后发现无效再回滚"的模式更安全，因为回滚可能不完整。

4. **渐进式能力叠加是 3-Story Epic 的有效拆分策略** — 19.1（基础执行）→ 19.2（自动调和）→ 19.3（动态扩展），每个 Story 在前一个的基础上叠加一层能力，同时保留前序 Story 的代码不变。这种拆分策略的关键成功因素是 19.1 的基础设计需要预留扩展点（如 IntentTree.Nodes map 支持动态添加、Engine 的 channel 事件模式被 Reconciler 复用）。

5. **IPC 扩展标准步骤已形成成熟的"六步法"** — 19.1 到 19.3 的 IPC 扩展严格遵循：(1) Method 常量 → (2) Request/Response 类型 → (3) Wire 类型 → (4) Server handler → (5) Adapter → (6) Client 方法。这与 Epic 18 发现的"AgentShell 语法扩展六步清单"形成对称——Rnix 项目中重复性工作已形成可文档化的标准流程。

**技术领域差异：**

Epic 20 与 Epic 19 的技术领域显著不同——从状态管理/事件驱动系统转向认知循环/自适应架构。关键挑战：

| 准备项 | 优先级 | 描述 |
|--------|--------|------|
| OODA 四阶段接入 ReasonStep 循环 | 关键 | 当前 ReasonStep 是线性 LLM 调用循环。OODA 需要在每轮 ReasonStep 中注入 Observe→Orient→Decide→Act 四阶段结构，这是对核心推理循环的重大修改 |
| Stem Agent Skill 匹配算法 | 关键 | 从意图文本中自动匹配最相关的 Skill 组合——需要语义匹配（LLM 或嵌入向量），不是简单的关键字匹配 |
| agent.yaml reasoning 字段扩展 | 重要 | 新增 `reasoning: ooda` 模式，需修改 agents/loader.go 解析逻辑和 kernel/process.go 的推理循环分支 |
| 分化记忆持久化 | 重要 | 分化路径（表观遗传）需要持久化到文件系统，是 intent 持久化问题的更大版本 |
| NFR41 OODA 框架开销 ≤ 200ms | 重要 | 四阶段循环的框架代码开销需控制在 200ms 以内，确保不拖慢推理速度 |

**无重大发现需要更新 Epic 20 计划。** Epic 19 的声明式意图与 Epic 20 的 OODA 循环是互补功能域：
- Intent 系统提供"目标声明和自动编排"
- OODA 提供"自主感知和决策循环"

**潜在风险：** Epic 20 的 Story 20.1 需要修改 kernel/process.go 的核心推理循环——这是 Rnix 最关键的代码路径之一（从 Epic 1 开始未有重大修改）。建议在 Story 20.1 开始前进行架构评审，确保 OODA 模式的接入不破坏现有线性推理的稳定性。
