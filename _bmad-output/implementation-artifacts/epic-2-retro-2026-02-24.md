## 做得好的（Successes）

### 1. types.DriverError 模式确立——驱动层错误处理标准

Story 2.2 经过两轮 Code Review 后确立了 `types.DriverError` 模式：驱动层统一使用 `*types.DriverError` 而非 `kernel.SyscallError`，VFS 层通过 `driverErrCode()` 辅助函数统一提取错误码。此模式直接让 Story 2.3（Shell 驱动）从第一轮就避免了依赖违规问题。

### 2. Epic 1 技术债一次性清理

Story 2.0 作为 Epic 2 的首个 Story，专门清理了 Epic 1 遗留的 3 个 HIGH 级问题（exit code 错误处理、result 截断、max_turns 语义）和 1 个 MED 级问题（VFSFile.Write context 传播）。这保证了后续 5 个 Story 在一个健康的代码库上开发，零驱动层回归。

### 3. 驱动开发模式成熟——可复用模板

从 LLM 驱动到 FS 驱动到 Shell 驱动，以下模式形成了可靠的模板：
- **Write-then-Read 语义** — 先 Write 请求，再 Read 结果
- **FileFactory 工厂模式** — 设备文件的创建模式
- **CommandBuilder 注入** — `exec.Command` 的可测试性方案
- **DriverError 统一错误** — 驱动层错误类型标准

### 4. 循环依赖干净解决

Story 2.4 需要 `kernel → skills` 导入，但 `skills → kernel` 已存在。解决方案简洁有效：将 `skills/loader.go` 中的 `kernel.NewSyscallError` 替换为 `fmt.Errorf`。这与 Story 2.2 中 `drivers/fs` 移除 kernel 依赖的思路一致，形成了"外围包不导入内核"的标准解耦方式。

## 挑战和问题（Challenges）

### 1. 架构依赖违规频繁（3/6 Story）

**频率：** 50%

- **Story 2.1**: `skills/loader.go` 导入 `kernel` 包（使用 NewSyscallError）
- **Story 2.2**: `drivers/fs/hostfs.go` 导入 `kernel` 包（使用 SyscallError）
- **Story 2.4**: `skills → kernel` 导致循环依赖（因 2.1 遗留的 kernel 导入）

虽然频率在下降（Story 2.3 和 2.5 从一开始就避免了），但 50% 的 Story 出现此问题说明依赖方向规则仅靠人的记忆不够可靠。

### 2. 错误类型不一致性（2/6 Story）

- **Story 2.2**: HostFSFile 中 Write 返回 `*kernel.SyscallError`，Read/Close 返回 `fmt.Errorf`——导致 VFS 层错误码传递不一致
- **Story 2.2 Round 2**: Write 返回 `fmt.Errorf` 但 VFS 层无法提取 `ErrPermission` 码——最终统一为 `*types.DriverError`

这暴露了在开始驱动开发前需要更明确的错误处理契约。

### 3. 防御性编程遗漏（2/6 Story）

- **Story 2.2**: `HostFSFile.Write` 不检查 closed 状态（Read/Close/Stat 均有检查）
- **Story 2.3**: Write 静默忽略非 ExitError 的 `cmd.Run()` 错误，返回 nil 伪装成功

这些都是 Code Review 发现的，开发阶段应该更自觉地检查所有方法的一致性。

### 4. 安全意识——路径遍历漏洞

**Story 2.4**: 设备权限白名单使用前缀匹配（`strings.HasPrefix(action.ToolPath, dev+"/")`），但未对 `action.ToolPath` 进行路径规范化。`/dev/fs/../shell` 能绕过白名单访问 `/dev/shell`。

Code Review 发现后通过 `path.Clean()` 在权限检查前规范化路径修复。但这暴露了安全相关代码需要更严格的审查流程。

## 关键洞察（Key Insights）

1. **Code Review 是最有效的安全网** — 架构违规、安全漏洞、防御性编程遗漏全部由 Code Review 发现。在 AI 辅助开发中，Review 的重要性不减反增。

2. **好的模式一旦确立会显著加速后续开发** — `types.DriverError` 模式让 Story 2.3 从第一轮就做对了驱动层错误处理。模式投资的回报是立竿见影的。

3. **技术债尽早清理回报巨大** — Story 2.0 清理 Epic 1 技术债后，后续 5 个 Story 零驱动层回归。这验证了"先还债再开发"的策略。

4. **依赖方向规则需要工具支撑** — 3/6 Story 违规说明光靠人的记忆和 Story 开发笔记中的警告不够。需要编译时或 CI 级别的自动化检查。

5. **安全相关代码需要专门审查** — 路径遍历漏洞说明权限检查代码不能只关注功能正确性，必须考虑恶意输入场景。
