### 业务成果

Epic 20 为 Rnix 引入了两大核心能力——**OODA 自主推理循环**和**干细胞分化机制**。这是 Rnix 从"用户驱动的工具型智能体"向"自主决策的认知型智能体"演进的关键一步。

**OODA 自主推理循环（20.1 + 20.2）：** 建立了完整的四阶段认知循环——Observe（纯框架环境感知）→ Orient（LLM 偏差评估）→ Decide（LLM 结构化决策）→ Act（执行决策并反馈）。核心设计决策是**OODA 作为独立推理模式与 reasonStep 并行存在**，零修改核心推理循环。通过 `agent.yaml` 的 `reasoning: ooda` 声明和 `SpawnOpts.ReasoningMode` 程序化接口双入口驱动。任务式指挥（Auftragstaktik）让 OODA 智能体可以自主 spawn 子智能体，只下达意图不规定执行细节。

**干细胞分化机制（20.3 + 20.4 + 20.5）：** 构建了从通用基底到特化智能体的完整链路——StemMatcher 关键词匹配（初始分化）→ DiffMemory 路径缓存（加速分化）→ OODASpecialize 动态 Skill 加载（渐进特化）→ Lineage 谱系追踪（可观测性）。Stem Agent 证明了"声明式配置 + 自动能力匹配"的智能体创建范式的可行性。

**OODA 和 Stem 的组合效应：** Stem Agent 默认使用 OODA 模式（`reasoning: ooda`），分化后的智能体在 OODA 循环中通过 specialize 动作按需扩展能力。这形成了"自动分化 → OODA 自主执行 → 动态特化 → 记忆加速"的完整闭环。

## 成功与优势

1. **OODA 零侵入接入——reasonStep 完全不变** — Epic 19 回顾中明确标注的最大风险是"修改 kernel/process.go 的核心推理循环"。最终的实现方案完美规避了这个风险：OODA 通过 Spawn 中 goroutine 启动点的 if/else 分叉选择，reasonStep 代码从 Epic 1 到 Epic 20 零修改保留。这是整个 Epic 最重要的架构决策，确保了 19 个 Epic 积累的线性推理稳定性不受影响。

2. **函数注入模式形成成熟的"注入链"** — 从 20.2 的 `agentLoader`，到 20.3 的 `stemMatcher` + `skillLoader`，到 20.4 的 `diffMemory`，KernelImpl 的依赖注入形成了清晰的模式：结构体/函数类型字段 + Setter 方法 + daemon 启动时注入。每个 Story 新增注入时零摩擦，因为模式完全一致。kernel 包不直接导入 agents/skills 包的具体实现，依赖方向严格单向。

3. **渐进式 Story 分层极其优雅** — 20.1（OODA核心）→ 20.2（声明式配置 + 任务式指挥）→ 20.3（Stem + 关键词匹配）→ 20.4（记忆 + 动态特化）→ 20.5（谱系可观测性），每个 Story 在前一个基础上叠加一层能力，且前序 Story 的代码几乎不需要修改。唯一的"回写"是后续 Story 在已有文件中添加新 case（如 oodaAct 的 switch 添加 specialize case），属于自然扩展而非重构。

4. **代码审查持续发现高价值问题** — 33 个审查问题（10H+16M+7L）中，HIGH 问题涵盖：TOCTOU 竞态（20.4）、静默吞掉 JSON 解析错误（20.2）、proc.Skills 未更新（20.3）、IPC wire format 违规（20.5）、AppendMessage 错误被忽略（20.4）。这些问题如果上线会导致数据不一致、静默失败或并发 bug。代码审查投入的价值持续得到验证。

5. **Stem Agent 的 NFR42 远超预期** — 关键词匹配算法实测 535us，远低于 3s 的 NFR42 要求。选择"不依赖 LLM 的关键词匹配"而非"LLM 语义匹配"是正确的——NFR42 在当前 skill 集规模下被关键词算法轻松满足，且无外部依赖。CJK 匹配局限性作为已知限制被正式记录。

6. **DiffMemory 的"记忆加速"设计精巧** — 首次 spawn 时走关键词匹配（~500us），记录分化路径到内存 map。第二次相同意图 spawn 直接从记忆复用（~10us），跳过匹配逻辑。normalizeIntent 通过 token 排序确保 "analyze code" 和 "code analyze" 命中同一缓存。LRU + 低频淘汰策略对 256 条目容量来说极其充裕。

7. **IPC 标准步骤在 20.5 再次验证** — Story 20.5 的 MethodLineage 严格遵循 IPC 4 步模式（protocol.go 类型 → server.go handler → client.go 方法 → cmd/rnix/lineage.go CLI），代码审查发现了 wire format timestamp 违反 int64 毫秒约定的问题（H1），证明标准步骤清单的检查价值。

## 挑战与成长领域

1. **代码审查 HIGH 问题密度偏高（10 个 HIGH / 5 个 Story = 2H/Story）** — 对比 Epic 19 的 2H+6M/3Story = ~2.7/Story（HIGH+MEDIUM），Epic 20 的 33 总问题/5Story = 6.6/Story。特别是 20.4（3H）和 20.5（2H）的 HIGH 问题集中在并发安全（TOCTOU）和协议一致性。这反映了 OODA 循环中进程状态的多线程修改（proc.mu + lineage.mu + diffMemory.mu）带来的并发复杂度上升。

2. **Story 20.2 混入 37 个不相关文件的重构** — 代码审查明确指出 `agents/types.go`、`kernel/kernel.go` 等文件中混入了 `strings.Builder`、`wg.Go()`、`slices.Contains` 等不属于 Story 20.2 的重构。这违反了"每个 commit 只包含 story 范围内的变更"原则。虽然重构本身有价值，但混入 story commit 会干扰代码审查和 git blame。

3. **CJK 意图匹配的已知限制未被解决** — Story 20.3 代码审查发现纯中文意图（如"分析代码"）无法匹配英文 skill 元数据（如 "code-analysis"）。StemMatcher 的关键词匹配基于空格/标点分词，CJK 字符无分词支持。这在一个 `communication_language: Chinese` 的项目中是实际影响较大的限制。当前方案：意图文本中包含英文关键词时可匹配（如 "analyze code 质量"），但纯 CJK 意图完全无法匹配。

4. **ooda-demo 示例 agent 引用不存在的 skill** — Story 20.2 创建的 `lib/agents/ooda-demo/agent.yaml` 引用了 `skills: [code-analysis]`，但 `lib/skills/code-analysis/SKILL.md` 不存在。运行时加载该 agent 会失败。虽然标记为 LOW（demo agent），但作为官方示例会误导用户。

5. **DiffMemory.Lookup 使用写锁，RWMutex 优化失效** — Story 20.4 的 Dev Notes 声称使用 RWMutex 优化"读多写少"场景，但 Lookup 因需更新 HitCount 而必须使用写锁。实际上 Record 和 Lookup 都是写操作，RWMutex 没有提供任何并发优化。这是"文档与实现不一致"的问题——代码是正确的，但设计文档的说明有误导性。

6. **CLI E2E 测试持续缺失（第八个 Epic）** — 20.5 新增的 `rnix lineage` 命令测试仍为 Cobra 注册级别的浅测试（TestLineageCmd_Registered、InvalidPID、NoDaemon）。从 Epic 14 延续至今第八个 Epic 未建立真正的 CLI 端到端测试框架。

## 关键洞察

1. **"并行推理模式"是修改核心循环的最安全策略** — OODA 没有修改 reasonStep，而是作为并行模式在 Spawn 的 goroutine 启动点分叉。这个策略的价值是：(a) 现有线性推理的全部测试自动成为回归保护；(b) OODA 的 bug 只影响 OODA 进程，不波及线性进程；(c) 未来新增推理模式（如 Plan-Do-Check-Act、Reflexion）可沿同一分叉点扩展。关键判断标准：当核心路径经过大量 Epic 验证后，**"添加并行路径"优于"修改现有路径"**。

2. **函数类型注入是 kernel 包管理外部依赖的最佳模式** — agentLoader、stemMatcher、skillLoader、diffMemory 四个注入形成了稳定模式：`type field func(...) (...)` + `SetXxx(fn)` + daemon 启动注入。这比接口注入更轻量（不需要定义接口），比直接导入更解耦（kernel 不知道 agents/skills 包的具体实现）。适用场景：kernel 需要调用外部包功能，但不希望持有外部包的直接依赖。

3. **内存缓存 + 规范化签名是轻量级"学习"的有效模式** — DiffMemory 的设计模式——normalizeIntent 生成规范化键 → map 存储 → Lookup 命中计数 → LRU 淘汰——是一种不依赖持久化的"运行时学习"。daemon 重启后冷启动（首次 spawn 走关键词匹配），热运行后加速（相同意图直接命中缓存）。这种模式可推广到 Rnix 的其他"频率优化"场景（如 IPC 方法调用统计、进程重启模式识别）。

4. **OODAActionType 的枚举扩展证明了 Act 阶段的可插拔性** — 从 20.1 的 4 种 action（tool_call/spawn/complete/replan）到 20.4 新增 specialize，oodaAct 的 switch 分支自然扩展。每个新 action 只需：(1) 定义常量；(2) 更新 oodaDecidePromptTemplate；(3) 添加 oodaActXxx 方法；(4) 添加 switch case。这形成了"OODA Act 扩展三步法"，未来新能力（如 communicate、delegate、learn）可按此模式添加。

5. **代码审查的 HIGH 问题集中在"并发状态修改"和"协议一致性"** — 10 个 HIGH 问题中，4 个与并发相关（TOCTOU、mutex 缺失、错误静默吞掉），3 个与状态一致性相关（proc.Skills 未更新、wire format 违规、HitCount 双重计数），3 个与错误处理相关（JSON unmarshal 静默、AppendMessage 静默、duplicate events）。这指向了一个系统性规律：**多线程进程状态修改是 bug 的热区**，Code Review 应将"mutex 覆盖范围"和"状态写入完整性"作为优先检查项。

### 团队协议

- **OODA 零侵入原则**：新增推理模式作为并行路径在 Spawn goroutine 启动点分叉，不修改 reasonStep 代码
- **函数注入模式**用于 kernel 外部依赖：`func(...) (...)` 字段 + Setter + daemon 启动注入
- **OODA Act 扩展三步法**：(1) OODAActionType 常量 (2) oodaDecidePromptTemplate 更新 (3) oodaActXxx 方法 + switch case
- **IPC 扩展标准步骤**（4-6 步）：protocol.go 类型 → server.go handler → client.go 方法 → CLI 命令
- **不相关重构**必须在独立 commit 中提交，不混入 story commit
- **Code Review 并发安全**重点检查：mutex 覆盖范围、TOCTOU 窗口、锁外状态读取、嵌套锁风险
- **DiffMemory 路径缓存**模式：normalizeIntent 生成规范化键 → map 存储 → Lookup 命中计数 → LRU 淘汰
- **动态 Skill 加载**通过 ctxMgr.AppendMessage 注入 body（与 gdb set skills 模式一致），AllowedDevices 追加权限
- Lineage 使用独立 mutex（不复用 proc.mu）避免嵌套锁
- CJK 意图匹配是已知限制——意图文本中需包含英文关键词
- ATDD 测试先行继续作为标准开发流程
- 所有测试启用 `-race`

**技术领域差异：**

Epic 21 与 Epic 20 的技术领域显著不同——从认知循环/自适应架构转向经济系统/质量评估。关键挑战：

| 准备项 | 优先级 | 描述 |
|--------|--------|------|
| Token 预算池跨进程分配模型 | 关键 | 当前 Budget 是每进程独立的（ContextBudget 在 SpawnOpts 中设置）。预算池需要共享状态和竞争调度，这是进程间资源管理的新维度 |
| 合约 SLA 评估框架 | 关键 | SLA 定义格式（agent.yaml/compose.yaml）、评估时机（进程退出时）、评估维度（质量/token/时间）都需要从零设计 |
| 声誉分数持久化 | 重要 | 声誉需要跨 daemon 重启保留——这是 Rnix 首次引入非 daemon 生命周期的持久化状态。DiffMemory（20.4）明确选择了不持久化，声誉系统不能做同样的选择 |
| SKILL.md synergy 字段扩展 | 重要 | 需要扩展 YAML frontmatter 格式，修改 SkillLoader 解析逻辑 |
| NFR43 预算分配 ≤100ms | 重要 | 跨进程预算调度需要高效的锁策略或 lock-free 设计 |

**无重大发现需要更新 Epic 21 计划。** Epic 20 建立的模式（函数注入、内存缓存、OODA 扩展机制）可被 Epic 21 复用，但 Epic 21 的核心挑战（跨进程资源管理、持久化状态、SLA 评估）是 Rnix 尚未涉足的新领域。

**潜在风险：** Epic 21 的 Story 21.1（Token 预算池）需要修改 compose 引擎和 Budget 管理系统——这涉及 Epic 7 和 Epic 10 的核心代码。建议在 Story 21.1 开始前评估 compose/budget 的当前架构是否支持预算池扩展，必要时先做重构准备。
