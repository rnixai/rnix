### 业务成果

Epic 21 为 Rnix 引入了三大核心能力系统——**Token 经济管理**、**质量声誉系统**和**Skill 协同效应**。这是 Rnix 从"功能完备的 Agent OS"向"自优化的智能平台"演进的关键一步。

**Token 经济管理（21.1）：** 建立了 Compose 编排层的共享 Token 预算池，实现了跨进程的资源管理——从 Epic 10.3 的单进程预算到多进程共享预算池，是 Rnix 资源管理维度的重大扩展。优先级驱动的配额分配让关键任务获得更多资源，预算耗尽机制防止资源浪费。

**质量声誉系统（21.2 + 21.3）：** 构建了从 SLA 约束定义、后置评估、声誉计分到自动择优选择的完整链路。SLA 评估是后置验证（不中断运行），声誉分数基于历史表现持续优化。`candidates` 字段让系统在多个候选 Agent 中自动选择表现最好的。这是 Rnix **首次引入非 daemon 生命周期的持久化状态**（JSON Lines 文件），标志着系统开始具备"学习"能力。

**Skill 协同效应（21.4 + 21.5）：** SKILL.md 的 `synergy` 字段让 Skill 作者可以声明组合涌现能力，DetectSynergies 纯函数在 system prompt 组装时自动检测并注入协同指令。组合矩阵记录历史表现，推荐标记帮助用户识别最有效的 Skill 组合。

**三大系统的协同效应：** Token 预算池管控资源 → SLA 评估度量质量 → 声誉分数引导选择 → Synergy 检测激活涌现 → 组合矩阵记录效果 → 反馈到声誉分数。这形成了"资源管理 → 质量评估 → 智能选择 → 能力增强 → 效果反馈"的完整闭环。

## 成功与优势

1. **JSON Lines 持久化模式形成标准范式** — ReputationStore（21.2）首创 JSON Lines 文件格式（一行一条 JSON 记录，追加写入），SynergyMatrix（21.5）直接复用此模式。选择 JSON Lines 而非嵌套 JSON 或 SQLite 是正确的——追加写入性能好、无需读取整个文件、便于调试查看、与 Rnix "一切皆文件"哲学一致。

2. **IPC 4 步扩展模式已成为团队肌肉记忆** — Epic 21 新增了 4 个 IPC 方法（budget_status、sla_status、reputation_status、synergy_list），每个都严格遵循 protocol.go → server.go → client.go → CLI 的 4 步标准流程。project-context.md 中的 IPC 扩展标准步骤已在 Epic 20 后正式文档化，Epic 21 证明了文档化的价值——零偏差执行。

3. **Code Review 问题密度大幅下降** — Epic 21 的 11 个问题（5H+4M+2L）/ 5 Story = 2.2/Story，对比 Epic 20 的 33 个问题（10H+16M+7L）/ 5 Story = 6.6/Story，**问题密度下降 67%**。HIGH 问题从 2H/Story 降至 1H/Story。这反映了 Epic 21 的技术领域（数据模型+计算+存储）比 Epic 20（并发状态机+多线程推理循环）更"安全"，也说明 Epic 20 回顾中确立的并发安全检查清单在 21.2 中发挥了作用。

4. **SLA 评估的"后置验证"设计避免了系统耦合** — SLA 评估在智能体完成后执行，不中断运行中的进程。这避免了 SLA 检查与 reasonStep 的耦合。运行时预算控制由 BudgetPool（21.1）和 ContextBudget（10.3）处理，SLA 是质量度量而非执行控制。职责划分清晰。

5. **Compose Engine 的 setter 注入链优雅扩展** — budgetPool（21.1）→ reputationStore（21.2）→ synergyMatrix（21.5），三个注入遵循完全一致的模式：`Engine.xxxField` + `SetXxx()/NewEngineWithXxx()` + daemon 启动注入。与 Epic 20 的 kernel 函数注入链呼应，形成了两层注入模式：kernel 层用函数类型注入（agentLoader/stemMatcher），compose 层用 setter 注入（budgetPool/reputationStore/synergyMatrix）。

6. **DetectSynergies 的纯函数设计** — `skills.DetectSynergies(skills []*SkillInfo) []string` 是无状态、无副作用的纯函数，输入 Skill 列表，输出涌现指令列表。算法 O(N*M) 对合理规模远低于 100ms NFR46 要求。这种设计使得 synergy 检测可被任何调用者复用，且测试极其简单。

7. **向后兼容策略一致且彻底** — 所有 5 个 Story 都有明确的向后兼容保证：无 token_budget 时不创建 BudgetPool、无 SLA 时不评估、无声誉数据时返回默认中性分（0.5）、无 synergy 字段时 Synergies=nil、candidates/alternatives 为空时不触发自动选择。每个 Story 都有对应的向后兼容测试。

## 挑战与成长领域

1. **Story 21.1 的 4 个 HIGH 问题揭示了"集成点"是 bug 热区** — 4 个 HIGH 中，3 个与 Engine 集成有关：ipcKernelSpawner.GetTokensUsed 是 stub（H1）、Engine 用本地计数器而非 BudgetPool.IsExhausted()（H2）、AllocateQuota 从未被调用（H3）。这些都是"正确实现了组件，但组件间的连接线没接好"的问题。说明跨模块集成时，不仅要测试每个组件，还要测试"谁调用谁"的连接点。

2. **ReputationStore 的竞态条件（21.2 H1）暴露了 SyncMap 模式的局限** — `RecordSLAResult` 的 Load+Modify+Store 操作在 SyncMap 上不是原子的，需要额外的 Mutex 保护。这是一个反复出现的模式：SyncMap 保证单次操作的并发安全，但多步操作（read-modify-write）仍需外部锁。建议在 project-context.md 中记录此注意事项。

3. **Engine 层与 Kernel 层的 BudgetPool 集成不完整（21.1 H4 未修复）** — Engine 从未调用 `kernel.RegisterBudgetPool()`，导致 IPC budget_status 始终返回 NOT_FOUND，kernel reasonStep 也无法找到 pool。标记为"out of scope"因为需要 compose-to-kernel 的 process group ID 传递，但这意味着 IPC 查询路径在生产环境中不可用。

4. **CLI E2E 测试持续缺失（第九个 Epic）** — 21.3 的 `rnix reputation` 和 21.5 的 `rnix synergy list` 命令测试仍为 Cobra 注册级别或 mock 连接级别的浅测试。从 Epic 14 延续至今的 CLI E2E 测试框架缺失问题已是第九个 Epic 未解决。

5. **Compose Engine 的 executeNode 方法职责不断膨胀** — 每个 Story 都在 executeNode 中追加逻辑：21.1 配额分配和消耗记录、21.2 SLA 评估和声誉记录、21.3 自动选择、21.5 synergy 记录。executeNode 正在从"执行单个节点"演变为"执行节点 + 资源管理 + 质量评估 + 声誉记录 + 组合追踪"的超级方法。

6. **Engine 注册到 Kernel 的 BudgetPool/SLAResult 需要手动连接** — 21.1 的 BudgetPool 注册和 21.2 的 SLAResult 注册都需要 Compose Engine 主动调用 Kernel 方法。但 daemon 初始化代码（cmd/rnix/main.go 的 runDaemon）中这些连接并非自动的——需要开发者手动确保注入链完整。

## 关键洞察

1. **"持久化状态"是平台成熟度的分水岭** — Epic 21 之前，Rnix 的所有状态（进程表、上下文、DiffMemory）都是 daemon 生命周期内的内存状态。ReputationStore 和 SynergyMatrix 引入了首次跨 daemon 重启的持久化数据。这意味着 Rnix 开始具备"记忆"——上一次运行的 Agent 表现会影响下一次的选择。文件持久化（JSON Lines）是 MVP 正确选择，但未来可能需要考虑数据增长（JSON Lines 文件会持续增长）和清理策略。

2. **"后置评估 + 持久化 + 反馈选择"是轻量级机器学习的等价物** — SLA 评估（度量）→ 声誉分数（聚合）→ SelectBest（决策）→ 执行结果（反馈）→ 新的评估...这是一个简化的强化学习循环。当前的 Score = 0.7 * SuccessRate + 0.3 * TokenEfficiency 公式足够 MVP，但其核心价值在于建立了"度量 → 聚合 → 决策 → 反馈"的基础设施。未来可以在此基础上引入更复杂的评分模型，而无需改变数据流。

3. **Compose Engine 的 setter 注入链暗示了"中间件"模式的需求** — budgetPool、reputationStore、synergyMatrix 三个注入在 executeNode 中的行为模式高度一致：节点执行前做准备（配额分配/agent 选择）、执行后做记录（消耗/SLA 评估/组合记录）。这本质上是"中间件"模式——before/after hooks 包裹核心执行逻辑。如果未来 Epic 继续在 executeNode 追加逻辑，应考虑将其重构为中间件链。

4. **SKILL.md 的 synergy 声明是"声明式涌现"的开创** — 传统做法是在代码中硬编码 Skill 组合的特殊逻辑。synergy 字段让 Skill 作者（而非平台开发者）声明组合效应，系统自动检测和注入。这是"声明式配置驱动行为"哲学在能力增强领域的延伸。与 Epic 20 的"声明式 agent.yaml reasoning:ooda"异曲同工。

5. **Code Review 问题密度是代码复杂度的代理指标** — Epic 20 的 6.6 issues/story（多线程认知循环）vs Epic 21 的 2.2 issues/story（数据模型+计算+存储），3 倍差距反映了技术领域的固有复杂度差异。并发状态机天然比数据处理管道更容易出错。这为未来 Epic 的风险评估提供了量化参考：涉及并发状态修改的 Story 应预留更多 CR 时间。

### 团队协议

- **JSON Lines 持久化模式**用于跨 daemon 重启的数据存储：一行一条 JSON 记录，`os.OpenFile` 追加写入 + `bufio.Scanner` 逐行读取
- **IPC 扩展标准 4 步骤**（已文档化并验证）：protocol.go 类型 → server.go handler → client.go 方法 → CLI 命令
- **Compose Engine setter 注入模式**：`Engine.xxxField` + `SetXxx()` setter + daemon 启动注入
- **SyncMap 多步操作需外部锁**：Load+Modify+Store 不是原子的，需额外 Mutex
- **SLA 评估是后置验证**，不中断运行中的进程——运行时限制由 BudgetPool/ContextBudget 处理
- **向后兼容策略**：新增可选字段 + nil/零值时跳过 + 对应的向后兼容测试
- **DetectSynergies 纯函数模式**：无状态、无副作用，输入数据输出结果
- **声誉默认分 0.5**：新 Agent 不被惩罚也不被优先
- **不相关重构**必须在独立 commit 中提交（继承自 E20）
- **Code Review 并发安全**重点检查（继承自 E20）
- ATDD 测试先行继续作为标准开发流程

**技术领域差异：**

Epic 22 与 Epic 21 的技术领域再次显著不同——从经济系统/质量评估转向安全监控/自愈系统。关键挑战：

| 准备项 | 优先级 | 描述 |
|--------|--------|------|
| Immune Daemon 架构设计 | 关键 | 行为监控需要持续采样 syscall 事件——是独立 goroutine 还是 hook 到现有 SyscallEvent 流？NFR44 要求 CPU 开销 <= 3%，架构选择影响性能 |
| 行为基线模型设计 | 关键 | Normal Profile 需要定义哪些指标（syscall 频率、资源访问模式、token 消耗速率）、基线计算方法（移动平均/百分位数/标准差）、数据存储格式 |
| 进程挂起（Suspend）机制设计 | 重要 | 异常检测后自动挂起进程——是新增 Suspended 状态到进程状态机（影响 Epic 1 核心），还是复用 SIGPAUSE（影响 Epic 6 信号系统）？需评估两种方案的侵入性 |
| 能力迁移上下文传递 | 重要 | 22.4 需要将"未完成的任务上下文"从故障 Agent 迁移到替代 Agent——context 数据如何跨进程复制？ContextManager 是否支持？ |
| 协作拓扑可视化 | 一般 | `rnix topology` 需要展示节点+边的图形——终端 ASCII art 还是 JSON 输出供外部工具渲染？ |

**对 Epic 21 技术的复用机会：**

| Epic 21 资产 | 复用场景 | 说明 |
|---|---|---|
| JSON Lines 持久化 | 22.1 行为基线存储、22.2 威胁记忆存储 | 复用 ReputationStore/SynergyMatrix 的 JSON Lines 模式 |

**无重大发现需要更新 Epic 22 计划。** Epic 21 建立的持久化模式和 IPC 标准可被 Epic 22 直接复用。但 Epic 22 的核心挑战（行为监控、异常检测、进程挂起）涉及 Rnix 核心进程状态机的潜在修改——这是 Epic 1 以来首次触及进程状态机扩展。需要特别谨慎，参考 Epic 20 的"零侵入 reasonStep"成功经验。

**潜在风险：** Epic 22 的 Story 22.2（异常检测后自动挂起）可能需要扩展进程状态机（新增 Suspended 状态），这将影响 Epic 1 建立的核心状态转移规则。建议在 Story 22.1/22.2 开始前评估挂起机制方案（新状态 vs 复用 SIGPAUSE），必要时先做架构决策。
