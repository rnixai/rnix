### 业务成果

Epic 22 为 Rnix 引入了完整的**安全防护与自愈能力**——Immune Daemon 持续监控智能体行为、自动检测异常并挂起威胁进程、在 Agent 故障时自动迁移能力到替代 Agent、通过协作拓扑优化多智能体协作路径。这是 Rnix 从"功能完备的 Agent OS"到"具备自我保护和自我修复能力的智能平台"的关键跃迁。

**行为监控与免疫系统（22.1 + 22.2）：** ImmuneDaemon 采用事件驱动架构（非轮询），通过 OnProcessStart/OnSyscallEvent/OnProcessExit 三个钩子被动接收事件，空闲时 CPU 开销为零（满足 NFR44 ≤3%）。NormalProfile 基于统计建模（均值+标准差），AnomalyDetector 使用 3σ 阈值检测异常（99.7% 置信区间）。威胁签名提供快速路径匹配，优先于统计检测。自动挂起复用 SIGPAUSE/SIGRESUME 信号系统（Epic 6.4），零侵入核心进程状态机。

**安全状态与可观测性（22.3）：** SecurityStatus 摘要（ok/warning/critical）提供系统安全态势的一目了然视图。Uptime 追踪和 SuspendedPIDs 列表让运维人员快速定位问题。增量扩展 22.1/22.2 的 IPC 响应结构，向后兼容。

**能力迁移与自愈（22.4）：** SimilarityMatrix 基于 Jaccard 系数计算 Agent 能力相似度（70% Skill 重叠 + 30% 协作历史加权），当 Supervisor 重启超限后自动选择最相似且声誉最好的替代 Agent（相似度×0.6 + 声誉×0.4）。与 Supervisor 树（Epic 10.4）和声誉系统（Epic 21.3）深度集成。

**协作拓扑与强化（22.5）：** 类型化协作记录（区分 Spawn 和 IPC 消息）构建实时协作图。强化路径自动识别高频协作对（阈值≥5），为 Compose 编排提供优先建议。`rnix topology` 作为顶级命令提供拓扑可视化。

**五大子系统的协同效应：** 行为监控（22.1）采集数据 → 异常检测（22.2）发现威胁 → 安全状态（22.3）汇总态势 → 能力迁移（22.4）自动恢复 → 协作拓扑（22.5）优化协作。这形成了"监控 → 检测 → 响应 → 恢复 → 优化"的完整安全闭环。

## 成功与优势

1. **事件驱动架构是正确的性能选择** — ImmuneDaemon 不做轮询，通过三个钩子被动接收事件。空闲时 CPU 开销为零，完美满足 NFR44 的 ≤3% CPU 要求。这与 Rnix 的"一切皆事件"哲学一致。

2. **复用 SIGPAUSE/SIGRESUME 而非新增进程状态** — Epic 21 回顾中担心 22.2 可能需要修改核心进程状态机（新增 Suspended 状态），最终选择了复用 Epic 6.4 的信号系统。零侵入核心，与 Epic 20 的"零侵入 reasonStep"是同一个智慧。

3. **Code Review 问题密度创历史新低** — 0.6/Story（0 HIGH + 3 MEDIUM），对比 Epic 20 的 6.6/Story 和 Epic 21 的 2.2/Story。三个 Epic 的问题密度持续下降 67% 和 73%。3 个 MEDIUM 问题全部是 File List 准确性问题，非代码问题。

4. **依赖注入模式一致且成熟** — 22.2 的 `suspendFn` 回调和 22.4 的 `migrateFunc` 回调通过函数类型注入避免循环依赖。与 Epic 20 的 agentLoader/stemMatcher（kernel 层函数注入）、Epic 21 的 Compose setter 注入形成三层一致的解耦模式。

5. **增量扩展模式成功** — 5 个 Story 在同一个 `kernel/immune.go` 文件上有机生长。每个 Story 在前一个基础上追加功能，从未打破已有测试。API 设计从 22.1 开始就足够稳定。

6. **22.2 的"前置实现"策略** — 22.2 的核心功能（AnomalyDetector、ThreatSignature、自动挂起）在 22.1 实现过程中就预置了 Tasks 1-4。开发者在 22.1 时有全局视野，为后续 Story 铺路，大幅降低了 22.2 的实际工作量。

7. **IPC 4 步标准继续零偏差执行** — 4 个新增 IPC 方法（immune_status, immune_resume, similarity_query, topology_query）全部严格遵循 protocol.go → server.go → client.go → CLI 的 4 步标准。这是从 Epic 20 开始连续第三个 Epic 的完美执行。

8. **nil 保护覆盖全面** — 所有新增公开方法都检查 receiver 是否为 nil（ImmuneDaemon/AnomalyDetector/SimilarityMatrix 等），nil 时静默返回零值。向后兼容策略贯穿始终。

## 挑战与成长领域

1. **DurationMs 亚毫秒截断（22.1）** — 当进程生命周期不足 1 毫秒时，`time.Duration.Milliseconds()` 返回 0，导致行为样本的 DurationMs 为 0。修复方案是在 elapsed > 0 时强制最小值 1ms。这揭示了整数除法精度丢失是行为监控系统的常见陷阱。

2. **异步持久化导致测试 flakiness（22.1）** — OnProcessExit 最初使用异步 goroutine 进行持久化，导致持久化操作和测试断言之间存在竞态。改为同步执行后问题消失。教训：在测试环境中，异步操作是 flakiness 的主要来源。

3. **类型对齐问题反复出现（22.1/22.3/22.4）** — `ActivePIDs` 和 `SuspendedPIDs` 从 `[]types.PID` 到 `[]uint64` 的 IPC 层转换在 3/5 Stories 中出现。IPC 层作为内部类型和外部 JSON 的边界，类型转换是不可避免的成本，但可以通过统一的转换辅助函数减少重复代码。

4. **Supervisor 迁移遗漏 Reap（22.4）** — Supervisor 迁移成功时遗漏了 `Reap(child.pid)` 调用，会导致被替代的进程变成僵尸。Code Review 发现此问题，非测试发现。说明进程生命周期的副作用（僵尸清理）在集成层面的测试覆盖仍需加强。

5. **File List 准确性是唯一反复出现的 CR 问题（22.3/22.4/22.5）** — 3/5 Stories 的 Code Review 都发现 File List 不完整或状态标注错误。虽然不影响代码质量，但影响 CR 流程效率。

6. **Go 1.26 新语法适配（22.3）** — `sync.WaitGroup` 的 `wg.Go()` 新模式和函数值比较的编译限制在测试代码中造成了 lint 和编译问题。团队需要持续跟进 Go 语言演进。

## 关键洞察

1. **事件驱动+回调注入是 Rnix 的"黄金解耦模式"** — Epic 22 的 ImmuneDaemon（事件钩子）、suspendFn（回调注入）、migrateFunc（回调注入）与 Epic 20 的 agentLoader/stemMatcher（函数注入）、Epic 21 的 Compose setter 注入形成了三层一致的解耦模式。建议在 project-context.md 中正式文档化为架构原则。

2. **单文件有机生长有极限** — `kernel/immune.go` 承载了全部 5 个 Story 的核心逻辑（15+ 类型和方法）。在 Epic 开发期间高效（单一上下文、减少导航），但作为长期维护单元可能过大。与 Epic 21 的 `executeNode` 膨胀是同一种味道，区别在于 `immune.go` 的关注点都在同一个领域。

3. **"纯内存 vs 持久化"的界限在 Epic 22 中出现了有意识的分化** — 行为基线（NormalProfile）和威胁签名（ThreatSignature）使用 JSON Lines 持久化，因为它们代表"学习到的知识"。协作历史（coopHistory/coopRecords）和迁移记录（MigrationResult）是纯内存的，因为它们代表"当前运行时状态"。这是 MVP 的合理选择。

4. **Code Review 问题密度持续三个 Epic 下降（6.6 → 2.2 → 0.6）** — 反映了团队工程成熟度的显著提升。部分归因于 Epic 22 的技术领域（行为监控/安全）比 Epic 20（并发状态机）更"安全"，但 0 个 HIGH 问题和整体趋势是实打实的。

5. **长期未触发行动项是回顾负担** — 从 Epic 16/19/20 继承的多个行动项已跨 3-7 个 Epic 未触发。这些项在回顾文档中占据空间但不产生价值。本次回顾决定归档 5 个长期未触发项。

- **事件驱动+回调注入**用于跨模块解耦——避免直接引用造成循环依赖
- **nil 保护**必须覆盖所有新增公开方法——receiver 为 nil 时静默返回零值
