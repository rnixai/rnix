### 业务成果

Epic 23 将 Rnix 从"单一 LLM CLI 驱动"演进为"灵活的多模型架构"。用户通过声明式 `rnix-providers.yaml` 配置文件即可接入任意 OpenAI 兼容 API（Ollama、Groq、DeepSeek 等），无需修改一行源码。

**配置驱动的 Provider 管理（23.1 + 23.2）：** 建立了完整的配置解析 → 驱动工厂 → VFS 注册链路。`DefaultProvidersConfig()` 保证零配置文件时行为与旧版一致（claude + cursor），消除升级摩擦。`DriverRegistry` 从闲置代码激活为驱动管理的统一入口。

**动态 Provider 解析（23.3）：** 移除了 kernel 包内的硬编码白名单 `allowedLLMProviders`，改为通过回调函数查询 `DriverRegistry`。新增 provider 时 kernel 代码零修改。错误消息自动列出所有可用 provider，用户体验大幅提升。

**安全的 API Key 管理（23.4）：** 环境变量引用模式确保 Key 不明文存储在配置文件中。Warning 日志仅输出变量名不输出值。缺少 Key 时 provider 仍注册（延迟验证），首次调用时通过 HTTP 401 → `ErrAuth` 链路提供运行时反馈。

**Provider Fallback 降级（23.5）：** 支持同 provider 内模型降级和跨 provider 降级两种模式。Fallback 在 reasonStep 中实现，遵循 VFS 标准 Open/Write/Read/Close 语义。Strace 事件完整记录 provider 切换过程。

**健康检查与可观测性（23.6）：** 异步健康检查不阻塞 daemon 启动，`HealthChecker` 可选接口让 CLI 类 driver 自然跳过。`rnix daemon status` 新增 provider 健康状态输出，IPC 4步标准流程再次验证。

**多 Provider Compose/Init 支持（23.7）：** Compose 和 Init 配置均支持 `provider` + `model` 组合指定，三层优先级（agent级 > spec全局 > 系统默认）与 Model 处理方式完全对称。零 IPC 协议变更证明了前序 Story 23.3 的前瞻性设计（`SpawnRequest.Provider` 已预留）。

## 成功与优势

1. **"配置层 → 工厂层 → 注册层 → 解析层 → 应用层"的渐进式 Story 分层** — 7 个 Story 形成了清晰的能力叠加链：23.1（配置定义）→ 23.2（驱动工厂+VFS 注册）→ 23.3（动态解析+白名单移除）→ 23.4（安全凭证）→ 23.5（容错降级）→ 23.6（可观测性）→ 23.7（上层应用适配）。每个 Story 严格消费前序 Story 的交付件，无循环依赖、无回写修改。这是 Rnix 项目 Story 分层设计最干净的一个 Epic。

2. **代码缺陷密度极低——0 个 HIGH 级代码缺陷** — 24 个 Code Review 问题中，2 个 HIGH 均为文档/文件清单不一致（23.7 的 H1/H2），非代码逻辑错误。7 个 MEDIUM 中 4 个为文档问题、1 个为测试断言改进、2 个为日志风格建议。这是从 Epic 1 到 Epic 23 中 Code Review HIGH 代码缺陷数最少的 Epic。原因分析：(a) 配置解析/工厂模式/IPC 扩展均为成熟的设计模式，无并发复杂度；(b) 已有的 LLM 驱动层（ClaudeCliDriver/CursorCliDriver/OpenAICompatDriver）功能完备，本 Epic 大部分 Story 是"接线"而非"造零件"。

3. **ATDD 红绿流程执行彻底——7 个 Story 均有独立 ATDD 测试文件** — 从 23.3 开始，每个 Story 由 TEA agent 先写 RED phase ATDD 测试（全部 `t.Skip`），Dev agent 再实现 GREEN phase。这确保了：(a) 验收标准有可执行的测试锚点；(b) 实现完成时 ATDD 测试自动作为回归保护；(c) Code Review 可以对照 ATDD 检查覆盖完整性。151 个新增测试中约 100 个为 ATDD 测试。

4. **回调函数注入模式再次验证——第 5 个使用者** — Story 23.3 的 `SetProviderResolver(names, has)` 完美复用了 Epic 20 建立的模式（agentLoader → skillLoader → stemMatcher → diffMemory → providerResolver）。5 个注入点形成了稳定的 kernel 外部依赖管理范式，代码审查时仅需检查"新回调是否遵循既有模式"。

5. **已有代码的高复用率——23.4 仅需 ~8 行新代码** — `OpenAICompatDriver` 已有 `WithAPIKey()`、`doHTTP()` Authorization header 设置、`classifyHTTPError` 401→ErrAuth 映射。Story 23.4 的全部工作是在 `CreateDriver` 工厂函数中加一个 `os.Getenv` + `WithAPIKey` 调用。这证明了 Epic 2/9 建立的 functional options 模式和 driver 架构的可扩展性。

6. **IPC 4步标准在 23.6 第三次成功应用** — MethodProviderStatus 严格遵循 protocol → server → client → CLI 流程。通过闭包注入（`func() []ProviderStatusWire`）实现了 `ipc` 包与 `drivers/llm` 包的零直接依赖——`ipc/server.go` 不导入 `drivers/llm`，由 `main.go` 桥接。这是 IPC 解耦的最佳实践。

7. **HealthChecker 可选接口设计精巧——零破坏 LLMDriver 接口** — 如果在 `LLMDriver` 接口中新增 `HealthCheck` 方法，所有 3 个 driver 实现都需修改（ClaudeCliDriver/CursorCliDriver 需空实现）。通过定义独立的 `HealthChecker` 可选接口 + 类型断言 `drv.(HealthChecker)`，仅 `OpenAICompatDriver` 实现。未来新增 HTTP 类 driver 只需实现该接口即可自动支持健康检查。

## 挑战与成长领域

1. **两个 Story 文件 Status 标记为 "review" 而非 "done"** — Story 23.3 和 23.5 的文件内 Status 字段仍为 `review`，但 `sprint-status.yaml` 中已标记 `done`。这是连续第三个 Epic 出现 Story 文件与 sprint-status 不一致的问题（Epic 19 的 19.3 也有类似情况）。原因：dev-story 流程中 code-review 完成后未自动更新 Story 文件的 Status 字段。

2. **Code Review 文档问题占比过高（HIGH 全为文档问题）** — 23.7 的 2 个 HIGH 分别是"File List 遗漏文件"和"Task 描述与实际不符"。Epic 全局来看，24 个 CR 问题中约 10 个与文档/注释/命名有关，而非代码逻辑。这说明 Story 文件的"关键文件变更"列表和 Task 描述在实现过程中会偏移，但 code-review 阶段未及时同步。

3. **OODA reasonStep 的 fallback 未覆盖** — Story 23.5 明确标注 "oodaReasonStep 有独立的推理循环，本 Story 仅修改线性 reasonStep；OODA 可在后续 Story 扩展"。这意味着使用 `reasoning: ooda` 模式的智能体不享有 fallback 保护。考虑到 Epic 20 建立了 OODA 模式，且 OODA 智能体每轮 2-3 次 LLM 调用（比线性模式消耗更多 token），fallback 缺失对 OODA 的影响更大。

4. **healthCheck 与 fallback 无联动** — Story 23.6 明确标注 "fallback 基于调用失败触发，不依赖健康状态；未来可优化为优先选择 healthy provider"。当前 fallback 是"失败后重试"模式，不是"预防性路由"模式。如果主 provider 已标记 unhealthy，reasonStep 仍会先尝试调用它、失败、再触发 fallback——这是可避免的延迟。

5. **151 个新增测试全为单元/集成级别——无真正的 E2E 测试** — 与之前 Epic 类似，所有测试使用 mock VFS 设备、httptest server 等模拟环境。没有测试真正连接到 Ollama/Groq 等外部 provider 的端到端场景。这与 CLI E2E 测试持续缺失的技术债一致。

6. **Story 23.3 的 resolveLLMDevice nil 安全** — 当 `hasProvider` 回调为 nil 时（未注入 resolver），resolveLLMDevice 允许任何 provider 通过。这是有意的向后兼容设计，但在生产环境中如果 `SetProviderResolver` 被意外跳过，将导致静默错误（引用不存在的 VFS 设备在 Open 时才会失败，而非 Spawn 时提前拦截）。

## 关键洞察

1. **"激活闲置代码"比"从零构建"高效数个数量级** — Epic 23 的核心策略是将散落的已有代码（DriverRegistry、OpenAICompatDriver、WithAPIKey、FileFactory）统一到配置驱动的注册流程中。DriverRegistry 从 Epic 2 建立后闲置了 21 个 Epic，OpenAICompatDriver 从实现到真正挂载也经过了多个 Epic。这些代码在设计时预留了扩展点（functional options、接口抽象），使得本 Epic 的"接线"工作异常顺畅。教训：**预留扩展点的成本极低（一个接口、一个 option 函数），但未来激活时的收益极高**。

2. **"配置驱动"替代"硬编码"的关键在于默认配置的完备性** — `DefaultProvidersConfig()` 返回 claude + cursor 的默认配置，确保无 `rnix-providers.yaml` 文件时行为与旧版完全一致。如果没有这个默认回退，用户升级后必须创建配置文件才能启动 daemon——这是破坏性变更。`LoadOrDefaultProvidersConfig()` 的设计模式（文件存在则加载，不存在则默认，格式错误则报错）可推广到未来所有"从硬编码到配置驱动"的迁移。

3. **Story 文件的 "跨 Story 边界" 表格是最有价值的设计工具** — 每个 Story 文件中的"本 Story 不实现"表格明确列出了功能归属，有效防止了 scope creep。例如 23.2 明确标注"API Key 归属 23-4"，23.5 标注"OODA fallback 未规划"。这些边界在 dev-story 流程中被严格遵守——7 个 Story 无一出现 scope 越界。

4. **"零 IPC 协议变更"证明了前瞻性字段预留的价值** — Story 23.3 在修改 `resolveLLMDevice` 时，同步在 `ipc.SpawnRequest` 中预留了 `Provider` 字段并在 server.go 中传递到 `SpawnOpts`。到了 Story 23.7 需要 Compose/Init 传递 provider 时，IPC 层零修改——只需在 compose 桥接层填充已有字段。这种"消费方尚未到来时就预留生产方接口"的策略，避免了后续 Story 的协议升级成本。

5. **Code Review 的核心价值从"发现 bug"转向"保障一致性"** — 相比 Epic 20 的 10 个 HIGH（TOCTOU 竞态、JSON 静默吞掉等真实 bug），Epic 23 的 0 个 HIGH 代码缺陷说明配置/工厂/IPC 扩展模式已极其成熟。Code Review 在本 Epic 中的核心价值是：(a) 确保文档与代码一致（发现最多问题的领域）；(b) 确保架构模式一致性（如 IPC 4步、回调注入模式）；(c) 确保安全审计完备性（23.4 的 Key 不泄露检查）。

### 团队协议

- **配置驱动的 Provider 管理**通过 `rnix-providers.yaml` + `LoadOrDefaultProvidersConfig()`，新增 provider 零源码修改
- **默认配置回退模式**：`LoadOrDefault*()` 模式——文件存在则加载，不存在则默认，格式错误则报错
- **DriverRegistry** 作为 LLM 驱动的统一管理入口（注册、查询、健康状态、名称列表）
- **回调函数注入**继续作为 kernel 外部依赖标准模式（第 5 个使用者 SetProviderResolver）
- **IPC 4步标准**继续应用：protocol.go 类型 → server.go handler → client.go 方法 → CLI 命令
- **HealthChecker 可选接口模式**：不修改核心接口，通过类型断言检测可选能力
- **闭包桥接**解耦 IPC 与 driver 包（`func() []ProviderStatusWire` 而非直接导入 `drivers/llm`）
- **Fallback** 在 reasonStep 中实现，遵循 VFS 标准 Open/Write/Read/Close 语义
- **Agent YAML** 支持 `fallback_provider` 字段实现跨 provider 降级
- **Compose/Init** provider 优先级：agent级 > spec全局 > 系统默认（claude）
- ATDD 测试先行继续作为标准开发流程
- 所有测试启用 `-race`
- Story 文件 Status 在 code-review 通过后必须同步更新
