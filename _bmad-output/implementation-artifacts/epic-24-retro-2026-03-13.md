### 业务成果

Epic 24 将 Rnix 从"内部进程间 LLM 调用"扩展为"面向外部工具的标准 API 网关"。用户通过 `rnix serve` 一条命令即可启动 OpenAI 兼容 HTTP 服务器，让 Aider、Open WebUI、Python `openai` 库等任何支持 OpenAI API 的外部工具通过 Rnix 统一消费 LLM 能力——一个端口统一所有 LLM 访问。

**核心框架建立（24.1）：** 在 `ipc/` 包中新建 `http_openai.go`，使用 Go 标准库 `net/http` 建立 OpenAI 兼容 HTTP Server。7 个 OpenAI 类型（Request/Response/Chunk/Choice/ChunkChoice/Message/Usage）的 JSON tag 严格对齐 OpenAI API 规范。`parseModel("provider:model")` 路由函数是整个 Epic 的核心抽象——外部 model 参数通过一个函数即可映射到 Rnix 的多 Provider 架构。

**同步调用实现（24.2）：** 完成 `/v1/chat/completions` 的同步模式。消息转换链 `ChatMessage → llm.Message → LLMRequest → driver.Call → LLMResponse → ChatCompletionResponse` 是 Epic 24 最关键的数据流。Code Review 发现并修复了 2 个 HIGH 安全问题（MaxBytesReader 防 OOM、context.Canceled 处理客户端断开）。

**SSE 流式输出（24.3）：** 为 `stream: true` 请求实现完整的 Server-Sent Events 支持。`handleStreamingResponse` 使用 `http.Flusher` 逐 chunk 推送，支持客户端断开的 context 取消传播。Code Review 引入 `ChatDelta` 类型解决 omitempty 序列化问题，确保首个 chunk 包含 `role: "assistant"`。

**Provider 发现（24.4）：** `/v1/models` 端点让外部工具自动发现可用模型。双 entry 策略（provider 名 + provider:model）确保返回的 model ID 可直接用于 `/v1/chat/completions` 的 model 参数。健康状态过滤排除不可用 provider。

**一键启动（24.5）：** `rnix serve` 作为独立 Cobra 子命令，复用 `runDaemon` 完整的 Provider 初始化序列（`LoadOrDefaultProvidersConfig → NewDriverRegistry → RegisterProviders → RunHealthChecks`），但进程独立于 daemon。端口校验、信号处理、优雅关闭一应俱全。

## 成功与优势

1. **"渐进式 Stub 替换"模式——5 个 Story 完美协作** — 24.1 创建所有路由的 501 stub + 全部类型定义 → 24.2 替换 chatCompletions stub（同步） → 24.3 替换 stream:true 的 501 为 SSE → 24.4 替换 listModels stub → 24.5 添加 CLI 入口。每个 Story 都在替换前序 Story 留下的占位，形成了极其清晰的依赖链。这种模式避免了"一次性实现大功能"的风险，同时保证了每个 Story 都有可编译、可测试的交付件。

2. **核心代码高度集中——95% 的功能在 2 个文件中** — `ipc/http_openai.go`（~350 行）和 `ipc/http_openai_test.go`（~1600 行）承载了整个 OpenAI 兼容层。这种集中度带来了：(a) 代码审查效率极高——每个 Story 的 diff 在同一文件内即可理解全貌；(b) 类型复用自然——7 个 OpenAI 类型在 24.1 定义后被 24.2/24.3/24.4 直接使用；(c) 测试 helper 持续复用——`stubDriver`、`configurableDriver`、`newTestRegistry` 在跨 Story 间持续增强。

3. **零外部依赖——纯 Go 标准库实现** — 没有引入 gin/echo/chi 等 HTTP 框架，没有引入 SSE 库。Go 1.22+ 的 `http.NewServeMux` 方法匹配语法 (`"POST /v1/chat/completions"`) 足以覆盖 3 个路由的需求。`http.Flusher` 接口足以实现 SSE。`httptest.NewRecorder` 足以覆盖全部测试场景。这延续了 Rnix 项目"最小依赖"的一贯原则。

4. **Code Review 发现了真实的安全缺陷** — 24.2 的 2 个 HIGH 是本 Epic 最有价值的 CR 发现：(H1) 缺少 `context.Canceled` 处理导致客户端断开被错误映射为 502；(H2) 缺少 `http.MaxBytesReader` 导致无限制请求体大小（OOM 攻击向量）。这两个问题在单元测试中不易暴露（因为测试通常使用小请求体和正常连接），但在生产环境中可能造成严重后果。CR 的安全审计视角在本 Epic 中发挥了关键作用。

5. **Decision 13 架构决策的成功验证——HTTP 绕过 Kernel** — Epic 24 的核心架构决策是让 `OpenAIServer` 直接持有 `*llm.DriverRegistry` 只读引用，绕过 Kernel 和进程模型。这带来了：(a) HTTP 请求不创建 Rnix 进程，最小化开销（NFR50 验证通过：HTTP 处理 ≤ 50ms）；(b) `ipc/http_openai.go` 仅导入 `drivers/llm`，不导入 `kernel/`，依赖关系极简；(c) `rnix serve` 可独立于 daemon 运行，用户不需要先启动 daemon。

6. **测试 helper 的渐进式增强是高效测试的关键** — 24.1 创建 `stubDriver` + `newTestRegistry` → 24.2 增加 `configurableDriver`（可控 Call 行为） → 24.3 增加 `streamFn`（可控 Stream 行为）+ `makeStreamEvents`/`parseSSELines`/`parseSSEChunks` → 24.4 增加健康状态设置。到 24.5 时，测试基础设施已极其完备，新测试只需几行即可搭建。这种"测试 helper 随业务代码一起增量演进"的模式值得继续保持。

7. **完成速度极快——5 个 Story 单日完成** — Epic 24 的 5 个 Story 全部在 2026-03-13 同一天内完成（含开发、测试、Code Review、修复）。原因分析：(a) Epic 23 建立的 `DriverRegistry` 基础设施完备——Epic 24 只需做"协议翻译"；(b) OpenAI API 规范明确——类型定义和错误格式有清晰参考；(c) Story 分层清晰——每个 Story 的范围精确（stub 替换模式）；(d) 零外部依赖——无需调试第三方库集成问题。

## 挑战与成长领域

1. **24.2 的 2 个 HIGH 安全缺陷——HTTP 安全意识需加强** — `MaxBytesReader` 和 `context.Canceled` 处理是 HTTP 服务器的基本安全卫生，但在初次实现中被遗漏。这不是架构层面的问题，而是"从内部 IPC 思维切换到面向外部 HTTP 思维"时的盲区。Rnix 之前的所有 IPC 都是 Unix socket（受信任的本地连接），不需要考虑恶意请求体大小或客户端异常断开。HTTP 网关面向外部工具（甚至可能面向网络），安全要求截然不同。

2. **24.3 SSE 的 delta 序列化问题——OpenAI 规范的隐含细节** — `ChatDelta` 类型的引入是因为 `ChatMessage` 的 JSON 序列化在 delta 场景下行为错误——空 `role` 和空 `content` 字段不应出现在 JSON 中。OpenAI 的流式 API 规范中，首个 chunk 的 delta 含 `role: "assistant"` 但无 `content`，后续 chunk 仅含 `content`。这些细节在 OpenAI 文档中描述模糊，需要通过实际对比才能发现。

3. **24.4 和 24.5 的模型选择——Cursor 和非标准 Agent** — Story 24.4 使用了 Cursor IDE 的 `claude-4.6-opus-high-thinking` 而非项目标准的 Claude Opus 4.6。虽然结果质量无差异，但模型选择的不一致性可能导致 Dev Agent Record 的可比性降低。建议统一使用项目标准模型。

4. **端到端测试仍然缺失——AC #5 的 Python openai 库验证未执行** — Story 24.5 的 AC #5 要求"外部 Python 脚本使用标准 `openai` 库连接网关"，但实际验证仅为架构推理（"OpenAIServer 使用标准 HTTP 协议，openai 库可直接连接"）。这是一个合理的推断，但不是真正的端到端测试。类似地，AC #4 的并发测试也仅为 `net/http` 原生并发的架构论证。

5. **Story 24.5 的 serve 命令与 daemon 完全独立——可能的混淆** — `rnix serve` 独立于 daemon 运行，自行创建 `DriverRegistry` 和 `DeviceRegistry`。这意味着 `rnix serve` 和 `rnix daemon` 同时运行时，它们的 Provider 列表可能不一致（如果 `rnix-providers.yaml` 在两次启动之间被修改）。AC #3 的原始描述是"共享 daemon 已注册的驱动实例"，但实际实现选择了独立模式。这是一个合理的架构简化，但与 Epic 定义中的描述有偏差。

6. **Code Review 文档问题持续存在——与 Epic 23 相同模式** — 24.4 的 H1/H2 仍为文档/File List 不一致问题，与 Epic 23 回顾中行动项 #2（Story File List 核对）相同。Epic 24 中此问题虽有所改善（仅 24.4 出现），但未完全消除。

## 关键洞察

1. **"协议翻译层"是最清晰的 Epic 类型** — Epic 24 的本质是在已有的 `LLMDriver` 接口之上添加一层 HTTP 协议翻译。输入规范（OpenAI API）和输出接口（LLMDriver.Call/Stream）都是明确定义的，实现者的工作纯粹是"格式转换 + 错误映射"。这种 Epic 的特点是：(a) 架构决策少（Decision 13 已预先定义）；(b) 类型设计直接对齐外部规范；(c) 测试用例可从规范中直接推导。建议未来类似"协议适配"类 Epic 都采用此模式。

2. **"Stub 替换"比"Feature Flag"更适合渐进式交付** — 24.1 用 501 stub 占位，后续 Story 逐个替换为真实实现。相比 feature flag 模式（通过配置开关控制功能可用性），stub 替换更直接：(a) 替换就是实现，没有"开关残留"的技术债；(b) 测试可以直接验证"501 → 200 的状态变化"；(c) 每个 Story 的 diff 清晰——"移除 stub 代码 + 添加真实实现"。这种模式适合"同一端点渐进增强"的场景。

3. **HTTP 安全审计应成为 HTTP Story 的标准 Code Review 检查项** — Epic 24 的 3 个 HIGH 代码缺陷全部是 HTTP 安全问题（MaxBytesReader、context.Canceled 两处）。Rnix 过去 23 个 Epic 的 IPC 都是 Unix socket，Code Review 的安全关注点是"权限检查"和"线程安全"。HTTP 引入后，安全关注点应扩展为：请求体大小限制、超时设置（ReadHeaderTimeout 已在 24.1 CR 中添加）、错误消息不泄露内部细节、客户端断开处理。建议将这些作为 HTTP Story 的 CR 标准检查清单。

4. **`parseModel` 是 Epic 24 的"胶水函数"——从 model 参数到多 Provider 架构的桥梁** — 一个仅 10 行的函数（`strings.SplitN(model, ":", 2)`）连接了外部的 OpenAI model 参数格式和内部的 `DriverRegistry.Get(provider)` 查找。`/v1/models` 返回的 model ID 可直接传入 `/v1/chat/completions` 的 model 字段——这种一致性来自 `parseModel` 在两个端点中的共享使用。小函数大价值。

5. **Epic 23 的"激活闲置代码"策略在 Epic 24 再次验证——DriverRegistry 从"内部注册表"升级为"HTTP 网关后端"** — Epic 23 将 DriverRegistry 从闲置代码激活为多 Provider 管理入口，Epic 24 进一步将其升级为 HTTP 网关的后端数据源。`DriverRegistry.Get()`、`Names()`、`GetHealth()` 三个方法在 Epic 24 中被密集使用，但 Epic 24 未修改 `drivers/llm/` 的任何文件。这证明了 Epic 23 建立的 API 表面的完备性。

### 团队协议

- **OpenAI 兼容 HTTP Server** 通过 `ipc/http_openai.go` 实现，与 Unix socket IPC 平级但独立
- **HTTP 绕过 Kernel**：`OpenAIServer` 直接持有 `*llm.DriverRegistry` 只读引用（Decision 13）
- **parseModel** 是 model 参数到多 Provider 架构的统一桥梁——所有端点共享
- **Stub 替换模式** 用于同一文件内的渐进式功能交付——24.1 创建 stub，后续 Story 替换
- **SSE 流式输出** 遵循 `data: {json}\n\n` + `data: [DONE]\n\n` 格式，使用 `http.Flusher` 逐 chunk 推送
- **HTTP 安全检查清单**（新增）：MaxBytesReader + ReadHeaderTimeout + context.Canceled + 错误消息脱敏
- **rnix serve** 作为独立命令运行，复用 `LoadOrDefaultProvidersConfig` 配置路径
- **零外部 HTTP 依赖**：仅使用 Go 标准库 `net/http`
- ATDD 测试先行继续作为标准开发流程
- 所有测试启用 `-race`
- Code Review 的安全审计视角对 HTTP Story 尤为关键
