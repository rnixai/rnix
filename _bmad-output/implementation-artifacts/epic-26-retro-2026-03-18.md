### 业务成果

Epic 26 将 Rnix 从"双推理模式并行"架构转变为"单一统一循环"架构。核心价值：

**架构简化（26.1）：** 一次性删除 OODA 双推理路径（~2860 行），消除了代码库中最大的技术债之一。双模式维护负担、语义漂移风险和 ~20s 性能损耗全部消除。删除操作干净利落——`make all` 首次运行即通过。

**能力升级（26.2）：** 统一推理循环支持 7 种 ActionType，LLM 每步自主决策行为类型。Planning 从独立模式降级为可配置能力（`planning: true/false`），让 LLM 根据任务复杂度自主判断是否需要先规划再执行。parseAction 从固定 tool_call 解析升级为全类型分派，`json.RawMessage` 避免双重序列化。

**能力保留（26.3）：** Stem Cell 的动态 Skill 加载能力完整迁移到统一循环。TOCTOU 双重检查、DiffMemory 记录、Lineage 记录全部保留，API 签名与调用模式与原 OODA 实现一致。

**质量保障（26.4）：** 修复了 strace 分析发现的 2 个阻塞性 bug（VFS flags 硬编码、工具错误未注入上下文），新增熔断机制（连续 3 次失败自动终止）。12 个测试覆盖 9 个核心场景。

**文档对齐（26.5）：** 8 个文档文件更新，确保 PRD、架构决策、project-context 和 CLAUDE.md 与代码库完全一致。

## 成功与优势

1. **"删除→重建→迁移→加固→文档"五步递进——Story 依赖链设计完美** — 26.1 清除旧代码（干净的编译基础）→ 26.2 构建新框架（7 种 ActionType + switch 骨架）→ 26.3 迁移高复杂度能力（specialize 含 TOCTOU/DiffMemory/Lineage）→ 26.4 修 bug + 测试矩阵 → 26.5 文档收尾。每个 Story 的前序依赖明确、修改范围隔离。这种"先删后建"模式比"边改边修"风险低得多。

2. **净删除 ~2000 行代码——少即是多** — Epic 26 是罕见的"交付价值的同时让代码库变小"的 Epic。删除 ooda.go（531 行）、ooda_test.go（819 行）、ooda_reasoning_test.go（650 行）后，新增的统一循环代码仅 ~800 行（含测试），净减少 ~2000 行。代码库从"双模式维护"变为"单路径维护"，认知负担大幅降低。

3. **Sprint Change Proposal 流程验证——从问题发现到 Epic 交付全程高效** — Epic 26 的触发点是 Epic 20 交付后的 strace 分析（发现 6 个问题），通过 Sprint Change Proposal 正式评估（含 Party Mode 多智能体讨论），产出统一推理循环提案和实施就绪性报告，最终 5 个 Story 单日交付。航向修正流程从发现问题到解决问题的效率极高。

4. **parseAction 的 json.RawMessage 设计——避免双重序列化** — Story 26.2 将 `Data` 字段从 `map[string]any` 改为 `json.RawMessage`，这让 spawn/complete/replan 的 data 内容可以延迟解析，避免了 Marshal→Unmarshal→Marshal 的性能损耗。小改动大价值。

5. **gatedLLMFile mock——优雅的数据竞争修复** — Story 26.3 发现 ATDD 测试中 `proc.lineage` 设置与 reasonStep goroutine 存在数据竞争。解决方案是引入 `gatedLLMFile` mock（阻塞首次 LLM Read，直到测试设置完成后释放），而非简单加 sleep。这个 mock 在 26.4 中也被复用。

6. **VFS flags 降级的 "null" 边界发现** — Story 26.4 实现 isEmpty 检查时发现 `parseAction` 在 `data` 为 JSON null 时产生 `[]byte("null")` 而非 `nil` 或 `{}`。及时增加了 `"null"` 条件，避免了运行时的隐性 bug。这类 JSON 边界问题在多层序列化场景中很常见。

7. **ATDD 测试对齐度高——26-3 和 26-4 零差距** — Story 26-3 规划 17 个测试，实现 17 个（100%）。Story 26-4 规划 12 个测试，实现 12 个（100%）。对比 Epic 25 中 25.1 的 38→31（82%）和 25.2 的 31→16（52%），测试规划执行对齐显著改善。Epic 25 回顾中的行动项 3（ATDD 对齐检查）已见成效。

## 挑战与成长领域

1. **Epic 状态未及时更新** — Sprint-status 中 `epic-26: in-progress`，但 5/5 Story 已全部 done。Epic 状态需要在回顾后手动更新为 done。这个问题在多个 Epic 中反复出现，反映了 sprint-status 更新流程的自动化程度不足。

2. **Story 26.1 的 review 状态残留** — Story 26.1 文件中 `Status: review`（而非 done），但 sprint-status 已标记 done。状态不一致说明 Story 文件的 Status 字段更新有时被遗漏。

3. **Story 26.2/26.3/26.4 的实际 Story 编号调整** — Epic 定义中 Story 26.3 是 "Bug 修复——VFS Flags 降级、错误注入与熔断机制"，但实际实现中 Story 26.3 变成了 "Specialize 能力迁移"，原 26.4（Specialize）和 26.3（Bug 修复）互换了。Story 26.5（文档）也吸收了原 26.5（测试矩阵）的部分内容，实际执行与 Epic 定义的 Story 划分有差异。Sprint Change Proposal 在执行过程中做了适应性调整，但文档未反映最终的 Story 重排。

4. **无独立 Code Review 周期** — 与之前 Epic 不同，Epic 26 的 Story 记录中没有 SM Review / Code Review 段落。虽然代码变更质量高（大部分是"删除"或"从已验证代码迁移"），但缺少独立 CR 意味着潜在的集成遗漏无法被发现。Epic 25 的经验已证明 CR 在跨模块适配场景中的高价值。

5. **Spawn 错误路径的熔断计入范围扩展** — Story 26.4 在实现中发现 AC-5（spawn 失败计入熔断）需要涵盖所有 spawn 失败路径（agentLoader nil / agent load error / Spawn 调用 error），而非仅限于 `k.Spawn()` 返回 error。这是 AC 定义颗粒度不足的体现——"spawn action 执行失败"的含义需要更精确的界定。

## 关键洞察

1. **"先删后建"是重构类 Epic 的最优模式** — 先用一个完整的 Story 彻底删除旧代码（确保编译通过），再逐步重建新功能。这比"边改边修"有三个优势：(a) 删除 Story 极易验证（编译通过即成功）；(b) 后续 Story 在干净的代码库上工作，不存在新旧代码交叉引用的混乱；(c) 强制开发者从零开始思考新设计，而非被旧实现约束。Epic 26 的 26.1→26.2 依赖链完美验证了这一模式。

2. **"配置化降级 vs 模式淘汰"的正确选择** — Epic 26 没有将 OODA 降级为一个可选配置项（"reasoning: ooda"），而是彻底删除。原因：(a) OODA 路径存在无法在 linear 路径复现的 bug；(b) 双代码路径的维护成本高于统一路径的功能损失；(c) 统一循环的 7 种 ActionType 已覆盖 OODA 的所有能力。"删除代码"比"废弃代码"更有价值——废弃的代码仍会产生认知负担和编译负担。

3. **Sprint Change Proposal 是"航向修正"的标准流程** — Epic 26 不在原始 Epic List 中，而是通过 Sprint Change Proposal 在 Epic 25 交付后动态插入。这个流程包括：问题发现（strace 分析）→ 影响评估 → 方案设计（Party Mode 讨论）→ 变更审批 → 实施就绪性报告 → 执行。整个流程从发现到交付在同一天完成。对于"发现必须立即处理的技术债"的场景，Sprint Change Proposal 是正确的响应机制。

4. **"Planning 作为能力而非模式"的设计哲学** — 将 `planning: true/false` 作为可配置能力（默认启用），而非独立的推理模式。这意味着 LLM 可以自主决定是否需要先规划再执行，而非被人类预设的模式限制。这个设计选择体现了"信任 LLM 判断"的理念——LLM 比人类更适合判断当前任务的复杂度。

5. **技术债应在"发现时机成熟"时立即处理** — Epic 20 交付后发现 OODA 的 6 个问题，如果拖延到更晚处理，这些问题会随着代码库增长而更难修复。Epic 26 证明了"及时处理技术债"的价值——5 个 Story 单日完成，修复了 2 个 Critical bug，同时简化了架构。
