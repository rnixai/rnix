## 做得好的（Successes）

### 1. `debug/` 包零依赖违规——架构设计从根源消除问题

整个 Epic 4/4 Story **零依赖方向违规**。对比 Epic 2 的 3/6 Story 违规率（50%），这是显著进步。原因不是引入了自动化检查（Epic 2 的 Action Item #1 未执行），而是 `debug/` 包从 Story 3.1 开始就严格约束只依赖 `internal/types/` 和标准库。好的初始架构设计比事后检查更有效。

### 2. FormatEvent 纯函数设计——可测试性极佳

`FormatEvent(event types.SyscallEvent, opts Options) string` 作为导出的纯函数，不依赖任何 I/O 或外部状态。单元测试可以直接传参验证输出，测试覆盖全面且运行快速。这个设计模式值得在后续组件中复制。

### 3. Options.Formatter 依赖反转——优雅解决跨层依赖

Story 3.4 面临的挑战：`debug/` 不能导入 `internal/ui/`（依赖方向禁止），但 `Attach` 需要使用 lipgloss 格式化。解决方案：在 `Options` 中添加 `Formatter func(types.SyscallEvent) string` 函数字段，由 `cmd/rnix/main.go` 在运行时注入 UI 格式化器。经典的依赖反转，保留了 `FormatEvent` 作为无 UI 依赖的 fallback。

### 4. NFR3 延迟合规——充裕余量

`TestAttach_Latency` 测量延迟 ~92µs，远低于 NFR3 要求的 500ms。事件从 DebugChan 到终端输出的路径极短：channel select → FormatEvent（纯函数）→ fmt.Fprintln（unbuffered stdout）。

### 5. Code Review 持续发挥关键安全网作用

每个 Story 的 Code Review 都有实质性发现：
- Story 3.1：emitEvent nil 检查恢复、benchmark 测试
- Story 3.2：ANSI 颜色嵌套 Bug、Attach write error 静默丢弃

## 挑战和问题（Challenges）

### 1. ANSI 颜色嵌套 Bug 重复出现（2/4 Story）

**频率：** 50%

- **Story 3.2**: error+slow+color 时，灰色标注的 `ansiReset` 打断外层红色包裹。修复：error 行跳过灰色着色。
- **Story 3.4**: ErrorStyle 内嵌 MutedStyle/AgentStyle 导致非均匀红色。修复：重构为 plain text 拼接后整行 ErrorStyle 包裹。

根因相同（多层颜色样式嵌套时，内层 reset 破坏外层），但技术表现不同（raw ANSI vs lipgloss）。Story 3.2 修复后未提取通用教训，导致 Story 3.4 同类问题再现。

### 2. DebugChan 未关闭——测试与生产行为不一致

**严重度：** HIGH（已知限制，有明确修复路径）

`kernel/kernel.go:finishProcess()` 不关闭 `proc.DebugChan`。生产环境中，进程完成后 `Attach` 永远阻塞，用户必须 Ctrl+C 退出。AC #4（"进程完成时 strace 输出 detach 汇总后退出"）在生产环境中不工作。

集成测试通过手动 `close(proc.DebugChan)` 绕过——测试绿灯但生产行为不符。

**修复路径：** Epic 4 Story 4-2（孤儿进程 reparent 与 Zombie 自动回收）的资源释放流程包含关闭 DebugChan。

### 3. initKernel() 架构妥协

Story 3.3 为让 `rnix strace` 子命令访问进程表，从 `runRoot` 中提取 `initKernel()` 共享函数。但这意味着 strace 需要初始化完整 kernel（包括不必要的驱动注册），仅为读取一个进程信息。

Epic 4 的 `rnix ps` 和 `rnix kill` 将继续使用此模式，架构成本持续积累。代码中已标注 TODO。

### 4. 🚨 跨终端 kernel 状态隔离——strace 核心场景不可用

**严重度：** CRITICAL（回顾后真实环境验收发现）

**问题：** 每次运行 `./rnix` 都会通过 `initKernel()` 创建一个独立的、内存中的 kernel 实例。不同终端的 `rnix` 进程之间**没有共享状态机制**。

**复现步骤：**
1. 终端 1：`./rnix "分析 README.md"` → kernel A 创建 PID 1，agent 开始运行
2. 终端 2：`./rnix strace 1` → kernel B（全新实例），进程表为空，PID 1 不存在
3. 结果：`✗ PID 1: process not found`

**影响：** strace 的核心用户场景（"一个终端跑 agent，另一个终端 trace"）在当前架构下**完全无法工作**。同样影响 Epic 4 计划中的 `rnix ps` 和 `rnix kill`——所有需要跨进程访问 kernel 状态的子命令都有相同问题。

**根因：** 当前架构设计为单进程模型——kernel 状态仅存在于运行 agent 的 OS 进程内存中，缺少 IPC（进程间通信）基础设施。

**可能的解决方案：**
- **方案 A：Daemon 模式** — `rnix` 作为后台服务运行，子命令通过 Unix socket 与之通信
- **方案 B：共享状态文件** — kernel 状态序列化到文件系统（如 `/tmp/rnix/`），子命令读取
- **方案 C：嵌入式子命令** — strace/ps/kill 作为根命令的内置功能而非独立子命令（如 `rnix "分析 README.md" --strace`）

**注意：** 单元测试和集成测试全部通过——因为测试中 kernel 实例是共享的。这也是为什么此问题在 Story 开发和 Code Review 中未被发现，直到回顾后的真实环境验收才暴露。

## 关键洞察（Key Insights）

1. **好的架构约束从根源消除整类问题** — `debug/` 包零依赖违规证明：严格的初始设计比事后自动化检查更有效。Epic 2 Action Item "引入依赖方向自动化检查"未执行，但问题消失了——因为架构设计本身就约束了依赖方向。

2. **颜色/样式嵌套是需要专门警惕的 Bug 类别** — 两个 Story（50%）重复出现。不论使用 raw ANSI 还是 lipgloss，多层嵌套的 reset 冲突是通用问题。需要系统性预防而非逐案修复。

3. **测试绕过 ≠ 问题不存在** — DebugChan 案例：手动 close channel 让测试通过，但生产环境行为不同。测试绿灯不等于生产正确——当测试需要模拟 kernel 行为时，必须标记为"已知限制"。

4. **纯函数设计是可测试性的最佳保证** — `FormatEvent` 作为无副作用的纯函数，测试简单、可靠、快速。相比之下，需要 I/O 或状态的函数测试成本高且脆弱。

5. **依赖反转模式值得推广** — `Options.Formatter` 用函数类型字段实现跨层集成，避免了循环依赖。这个模式适用于任何"底层包需要使用上层能力"的场景。

6. **真实环境验收不可替代** — 跨终端 kernel 状态隔离问题在所有自动化测试中未暴露（测试共享 kernel 实例），直到回顾后手工验收才发现。这是连续三个 Epic 未执行真实环境验收的直接后果——该 Action Item 从 Epic 1 延续至今。

## Epic 4 准备评估

### 🚨 重大发现：跨终端 kernel 状态隔离影响 Epic 4

**回顾后真实环境验收发现：** 当前架构为单进程模型，每次 `rnix` 调用创建独立 kernel 实例，进程表不共享。这不仅影响 Epic 3 的 `rnix strace`，还**直接影响 Epic 4 计划中的所有子命令**：

| 计划中的命令 | 影响 |
|-------------|------|
| `rnix strace <pid>` (Epic 3) | ❌ 无法从另一个终端追踪运行中的 agent |
| `rnix ps` (Story 4-4) | ❌ 无法列出另一个进程中运行的 agent |
| `rnix kill <pid>` (Story 4-1) | ❌ 无法从另一个终端终止运行中的 agent |

**这意味着 Epic 4 在开始前需要解决 IPC 基础设施问题，否则 Story 4-1（Kill）和 Story 4-4（ps）将面临与 strace 相同的跨终端不可用问题。**

### 建议的应对策略

在开始 Epic 4 之前，需要先确定 IPC 方案并可能新增一个技术基础设施 Story：

- **方案 A：Daemon 模式** — `rnix` 以后台服务运行，子命令通过 Unix socket 通信。最完整但工作量最大。
- **方案 B：共享状态文件** — kernel 状态序列化到文件系统（如 `/tmp/rnix/`），子命令读取。中等复杂度。
- **方案 C：嵌入式子命令** — 重新设计 CLI 交互模式，ps/kill/strace 作为运行时交互功能而非独立子命令。最小改动但用户体验不同。

**建议：** 在创建 Epic 4 Story 之前，召开架构评审会确定 IPC 方案，并将其作为 Epic 4 的前置 Story（如 Story 4-0）。

### 依赖分析

Epic 4（进程管理与可靠性）依赖 Epic 3 的以下组件：

- **DebugChan 机制** — Story 4-2 资源释放需关闭 DebugChan（修复 Epic 3 H1）
- **strace 命令** — 与 `rnix ps`、`rnix kill` 并行使用
- **initKernel() 共享函数** — `rnix ps` 和 `rnix kill` 复用此模式（**但存在跨终端隔离问题**）
- **进程状态机** — Kill/Wait 操作依赖现有的 Created→Running→Zombie→Dead 转移

## 回顾结论

Epic 3 成功交付了 Rnix Agent OS 的调试追踪核心体验——从 SyscallEvent 记录基础设施、事件消费与格式化、CLI 命令到 lipgloss 样式化 UI。4 个 Story 全部完成，100% 交付率，自动化测试全部通过。

最重要的技术成就是 `debug/` 包零依赖违规的架构设计和 `Options.Formatter` 依赖反转模式。

**然而，回顾后的真实环境验收暴露了一个 CRITICAL 级架构问题：跨终端 kernel 状态隔离。** 每次 `rnix` 调用创建独立 kernel 实例，导致 `rnix strace <pid>` 无法从另一个终端追踪运行中的 agent。此问题同样影响 Epic 4 计划中的 `rnix ps` 和 `rnix kill`。

**核心教训：**

1. **自动化测试不能替代真实环境验收** — 此 CRITICAL 问题在所有单元测试和集成测试中均未暴露（因为测试共享 kernel 实例），直到手工跨终端验证才发现。这是"真实环境验收"Action Item 连续 3 个 Epic 未执行的直接后果。
2. **好的架构约束从根源消除整类问题** — `debug/` 包零依赖违规证明了初始设计的价值。
3. **但架构盲区同样会从根源上制造系统性问题** — 单进程 kernel 模型是一个架构假设，从未在真实多终端场景中验证。

**Epic 4 存在阻塞项：** 在确定 IPC / 跨进程状态共享方案之前，Story 4-1（Kill）和 Story 4-4（ps）无法有效实现其核心用户场景。建议在 Epic 4 开始前召开架构评审。
