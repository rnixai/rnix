## 做得好的（Successes）

### 1. "用户空间"架构模式第三次成功

`skillpkg/` 完全独立于 `kernel/`，不导入 `vfs/`、`agents/`，依赖方向严格单向：`cmd/rnix/ → skillpkg/ → skills/`。内核代码在 Epic 8 期间零修改。这是继 Epic 6（IPC 子接口）、Epic 7（compose/）之后，第三次验证"用户空间"组件模式。

### 2. 跨 Story 经验传递显著改善

Epic 8 的经验传递是项目最佳：
- Story 8.2 发现 Unicode 截断问题 → 8.3、8.4 Dev Notes 主动提醒
- Story 8.1/8.2 发现 nil slice vs 空 slice → 8.3 开始使用 `make([]T, 0)` 初始化
- Story 8.1 建立安全防护 → 8.2-8.4 自动继承
- Code Review 严重度趋势：8.1(9) → 8.2(10) → 8.3(5) → 8.4(6)

### 3. Story 粒度控制有效

所有 4 个 Story 均为 5 个 Task，严格遵守 Epic 7 回顾确立的"不超过 5 个 Task"约定。与 Epic 7 的 Story 7.2（8 Task、10 个审查问题）对比，Epic 8 最复杂的 8.1（5 Task、全新包+网络+安全）也控制在 9 个审查问题。

### 4. 安全基础设施一次性投资

Story 8.1 建立了完整的网络安全防护：
- tar 提取大小限制（`maxFileSize` 10MB + `maxTotalExtractSize` 50MB）
- HTTP 响应大小限制（`maxMetadataSize` 1MB + `maxPackageSize` 50MB）
- 路径遍历防护
- SHA256 校验强制验证
- 符号链接/硬链接显式拒绝

这些防护被 8.2-8.4 自动继承，无需重复实现。

### 5. AC 逐条验证制度落地

所有 4 个 Story 的 Code Review 包含 "AC Validation Summary"，逐条验证实现状态。Story 8.3 还发现 AC#2 的交互确认未实现并记录为 MVP 决策。这是 Epic 7 回顾 Action Item #3 的成功落地。

### 6. 模式复用成熟

Story 8.1 建立的 CLI 注册模式、JSON 输出模式、mock HTTP server 测试模式被 8.2-8.4 直接复用。每个后续 Story 不需要重新设计基础架构，只需在已有模式上扩展方法和子命令。

## 挑战和问题（Challenges）

### 1. Code Review 问题总数仍高

30 个问题与 Epic 7 的 29 个持平。虽然 HIGH 从 9 降到 7，但绝对数仍然偏高。特别是 Story 8.1 的 3 个安全 HIGH（zip bomb、HTTP 无界读取、符号链接）属于基本安全实践，不应到 Review 才发现。

根因：项目首次引入网络操作，缺乏网络安全反模式检查清单。

### 2. 死文件/死代码跨 4 个 Story 被标注但无人清理

`skillpkg/stubs_test_support.go`（空文件）和 `skillpkg/testdata/index.yaml`（未引用 fixture）从 Story 8.1 创建后，在 8.2、8.3、8.4 的 Dev Notes 中被反复标注"不要引用这些死文件"，但始终未删除。

根因：
- Story 范围定义不包含"前序清理"任务
- Code Review 的 LOW 项默认 "noted, not fixed"
- "不是我的 Story 范围"心态

### 3. Action Items 追踪机制连续两个 Epic 未建立

Epic 7 回顾承诺把 Action Items 写入 sprint-status.yaml，Epic 8 完全未执行。完成率 33%，与 Epic 7 的 30% 持平。追踪机制本身没被追踪——最讽刺的系统性失败。

### 4. reapProcess 集成测试和 pipeBuffer 容量限制第四次记录

这两个技术债从 Epic 5/6 开始记录，经过 Epic 7 和 8 均未处理。原因：Epic 7 和 8 都是"用户空间"组件，不触及 kernel/ 和 ipc/ 代码。但 Epic 9 将回到内核级修改，reapProcess 链需增加 MCP Unmount 步骤——没有集成测试的情况下修改 12 步释放链风险极高。

### 5. 终端输出缺少测试覆盖

JSON 输出测试完备，但终端表格渲染、错误消息格式、Tip 提示——用户直接看到的内容完全没测试。Story 8.2 和 8.4 的 Review 均标注了此问题。

## 关键洞察（Key Insights）

1. **"用户空间"组件模式是架构核心竞争力** — 连续三个 Epic（6、7、8）验证：独立包不修改内核，降低风险，加速开发，便于测试。Epic 9 回到内核修改时需格外谨慎。

2. **跨 Story 经验传递是 Epic 8 最大亮点** — 安全防护、Unicode 处理、空 slice 初始化等教训即时传播。每个 Story 的 Dev Notes "前序经验教训"章节是有效的知识传递机制。

3. **承诺不追踪 = 承诺消失，已连续两个 Epic 验证** — Action Items 完成率 30%→33%，无改善。口头承诺不够，需要可追踪的记录和检查点。

4. **首次网络操作引入新威胁模型** — HTTP client、tar 提取、外部数据处理需要专门的安全检查清单。project-context.md 的反模式列表需要扩展网络安全部分。

5. **"noted, not fixed" 不应是死代码的默认处理方式** — 死文件在 4 个 Story 中被标注但无人清理。Code Review 需要对死代码强制执行清理。

6. **Story 粒度控制确实影响质量** — 5 Task 上限有效，Code Review 问题量与 Story 复杂度正相关。Epic 9 回到内核修改时，Story 粒度控制更为重要。

## 回顾结论

Epic 8 是 Rnix 项目构建 Skill 包管理生态的里程碑。4 个 Story 全部完成，100% 交付率。`skillpkg/` 包通过严格的单向依赖独立于内核，是"用户空间"架构模式连续第三个 Epic 的成功验证。65 个新测试，16 个包零回归。

跨 Story 经验传递是 Epic 8 的最大亮点——安全防护、Unicode 处理、空 slice 初始化等教训即时传播，Code Review 严重度从 8.1 的 9 个逐步下降。Story 粒度控制（5 Task 上限）和 AC 逐条验证制度均成功落地。

然而，Code Review 问题总数（30）与 Epic 7（29）持平，Action Items 追踪完成率（33%）与 Epic 7（30%）持平，死文件在 4 个 Story 中被标注但无人清理。reapProcess 集成测试和 pipeBuffer 容量限制第四次出现在回顾中。

**核心教训：**

1. **"用户空间"组件模式是架构核心竞争力** — 三个 Epic 验证成功，Epic 9 回到内核修改时需格外谨慎。
2. **跨 Story 经验传递机制有效** — Dev Notes "前序经验教训"章节是知识传递的最佳实践。
3. **承诺不追踪 = 承诺消失** — 连续两个 Epic 验证，Action Items 追踪机制必须真正落地。
4. **死代码需要流程级清理** — "noted, not fixed" 不能成为 Code Review 的默认处理方式。
5. **首次网络操作需要安全检查清单** — project-context.md 需扩展网络安全反模式。
6. **Story 粒度控制质量** — 5 Task 上限有效，Epic 9 内核修改时更为重要。

**下一步：** Epic 9（MCP 服务集成）。两个 CRITICAL 阻塞项：reapProcess 集成测试和 MCP 协议技术 spike 必须在 Epic 9 开始前完成。
