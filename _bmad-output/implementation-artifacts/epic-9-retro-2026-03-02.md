## 做得好的（Successes）

### 1. 依赖倒置设计

MCPTransport 接口定义在 `vfs/mcp.go`，`drivers/mcp/transport.go` 实现该接口。VFS 层不依赖驱动层，完全遵循依赖方向规则。这是 Crux 项目首次在接口层面实现真正的依赖倒置，未来更换传输方式（stdio → SSE）只需在 drivers/mcp/ 新增实现，VFS 层零修改。

**Decker 评价：** 这是 Epic 9 最突出的成功——架构弹性的核心。

### 2. 四层能力栈完整验证

Agent（身份+策略）→ Skill（程序性知识+工具权限）→ MCP（外部服务集成）→ Device（原生 I/O）四层端到端通过。Story 9.4 的 24 个子测试覆盖了正常路径、边界条件、权限控制、astrace 可观测性。全部使用 mock，不依赖外部服务，测试稳定且可重复。

### 3. 跨 Story 经验传递持续改善

Dev Notes "前序经验教训"章节有效传递知识：
- Story 9.2 继承 9.1 的 TOCTOU 竞态教训 → PID 前缀隔离自然避免并发 Mount
- Story 9.3 继承 9.2 的 Lock 保护教训 → 并发字段访问正确加锁
- Code Review 严重度：9.1(9) → 9.2(7) → 9.3(6) → 9.4(9)（9.4 的 HIGH 都是文档类非代码缺陷）

### 4. readFromBuffer 重构

Story 9.3 从 mcpFile.Read() 中提取分块读取逻辑为 readFromBuffer 辅助函数，5 种 VFSFile 类型统一使用。消除代码重复的同时，通过 Code Review HIGH-1 的修复确保了行为一致性。

### 5. 测试设计质量

185 个新测试，3,998 行测试代码。关键亮点：
- 全 mock 设计：Agent/Skill/MCP/Device/LLM 各层独立 mock
- 表驱动测试：mcpFileFactory 路由 9 种子路径、Config 解析多种场景
- race detection 全部通过
- 17 包零回归

### 6. 进程隔离 MCP 挂载

使用 `{pid}-{server-name}` 路径前缀避免多进程引用同一 MCP 服务器时路径冲突，同时 finishProcess 自动 Unmount 确保进程退出时正确清理资源。

## 挑战和问题（Challenges）

### 1. StdioTransport.Ping/Connect 未完成

Story 9.1 的 Task 6.4（Ping health check）未完成，StdioTransport.Ping 是 no-op stub。StdioTransport.Connect 也未执行 MCP initialize 握手。两者都是 Code Review 的 HIGH 级别问题，以"MVP 可接受"为由未修。

影响：MCP 健康检查是假的——系统以为服务器正常，实际上什么都没检查。这在 Epic 10 的 Supervisor 树自动重启场景中会成为隐患。

**Decker 决策：** 必须立即修复，不推迟到后续 Epic。

### 2. bare error 反模式延续

所有 MCP 文件类型的 closed 状态检查返回裸 error 而非 DriverError。Story 9.3 Code Review 标记为 HIGH（HIGH-2）但以 "pre-existing pattern" 为由未修。这意味着 astrace 追踪链在 MCP 文件操作处断裂。

### 3. Code Review 问题总数连续 3 个 Epic 稳定在 30 左右

Epic 7(29) → Epic 8(30) → Epic 9(31)。HIGH 没有下降趋势（类型变化但数量稳定），LOW 在上升（5→10→12）。说明代码质量基线稳定但没有系统性改善。

根因：LOW 上升主要是收尾工作（文档准确性、Task checkbox、文件列表更新）不够仔细。

### 4. Action Items 完成率持续下降

Epic 7(30%) → Epic 8(33%) → Epic 9(14%)。7 个 Action Items 中只有 1 个确认完成。追踪机制本身（sprint-status.yaml action_items）第三次承诺第三次未执行。

**Decker 决策：** 不再口头承诺，所有改进项回顾后立即执行。

### 5. reapProcess 集成测试第五次未执行

从 Epic 5/6 开始记录，经过 Epic 7、8、9 均未处理。Epic 9 期间 reapProcess 被修改（在 Shutdown 中添加了 mountMgr.UnmountAll()、在 finishProcess 中添加了 MCP Unmount），但仍然没有集成测试。

## 关键洞察（Key Insights）

1. **依赖倒置是架构弹性的核心** — 接口在高层定义、实现在低层，让系统可扩展且低耦合。与"用户空间"组件模式互补。

2. **每个新技术领域都会带来新 HIGH 问题** — 经验传递有效但覆盖不了新攻击面。Code Review 的 HIGH 是进入新领域的固有成本。

3. **口头承诺不如直接执行** — 连续 3 个 Epic 验证：改进项必须当场落地，不能推迟。Action Items 追踪机制本身也需要追踪——最讽刺的系统性失败。

4. **LOW 问题上升需要自检步骤** — 开发完成后增加收尾自检（检查死代码、更新文档、验证 Task checkbox）可以在 Review 前消除大部分 LOW。

5. **四层能力栈是 Crux 的核心价值主张** — Agent → Skill → MCP → Device 四层职责分离并端到端验证成功，为 Epic 10 的 Supervisor 容错提供了坚实基础。

6. **Code Review 总数稳定在 30** — 需要区分对待：HIGH 是新领域成本（难以避免），LOW 是流程问题（可以改善）。

## 回顾结论

Epic 9 是 Crux 项目实现 MCP 服务集成的里程碑。4 个 Story 全部完成，100% 交付率。依赖倒置设计（MCPTransport 接口定义在 vfs/、实现在 drivers/mcp/）是架构层面的核心成就。四层能力栈（Agent → Skill → MCP → Device）端到端验证通过，标志着 Crux 的核心价值主张首次完整实现。

185 个新测试、3,998 行测试代码、17 包零回归——测试质量是 Epic 9 的亮点。跨 Story 经验传递继续改善，readFromBuffer 的重构消除了代码重复。

然而，Code Review 问题总数（31）与前两个 Epic（29、30）持平，LOW 上升趋势（5→10→12）表明收尾工作需要自检步骤。StdioTransport.Ping/Connect 未完成和 bare error 延续是需要立即修复的 HIGH 级别技术债。Action Items 完成率（14%）创历史新低。

**核心教训：**

1. **依赖倒置是架构弹性的核心** — 与"用户空间"组件模式互补。
2. **新技术领域带来新 HIGH** — 经验传递覆盖不了新攻击面。
3. **口头承诺不如直接执行** — 连续 3 个 Epic 验证，改进项必须当场落地。
4. **LOW 上升需要自检** — 收尾自检可以在 Review 前消除大部分 LOW。
5. **四层能力栈是 Crux 的核心价值主张** — 端到端验证成功。

**下一步：** 回顾后立即执行 6 个改进项（死文件清理、Ping/Connect 实现、reapProcess 集成测试、bare error 修正），然后启动 Epic 10（监控、Supervisor 与运维）。
